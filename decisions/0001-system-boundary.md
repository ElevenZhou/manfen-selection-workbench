# 决策记录：0001 系统边界与部署形态

日期：2026-11-24  决策人：CEO / 老大

## 背景与事实

现有选品站点已经具备报告、候选、资料包和飞书闭环；新目标增加账号、长任务、人员容量、认领和服务器上的研究执行器。这些能力需要持久 Worker、队列、租约和稳定的内部网络。

## 选项

1. 继续只用现有 Sites/D1。
2. Web 留在边缘平台，长任务另挂服务器。
3. Web/API、数据库、队列和执行器统一放在自有服务器，Cloudflare 做边缘层。

## 决定

采用选项 3 作为生产目标；MVP 可先用本地 Docker Compose 和一台 staging 服务器验证。现有站点作为报告迁移/兼容来源，不直接删除或重建历史数据。

## 理由

长任务、浏览器、Codex/OpenCode/Hermes 和租约回收在自有服务器上更容易控制；统一部署能简化审计、备份、内网和回滚。代价是需要自己承担运维、监控和安全，必须先完成 staging 与 canary。

## 复查条件

当每日任务量、成本或可用性证明单机不够时，再拆分 Worker、数据库和执行器；没有真实指标前不提前购买复杂集群。
