# 明早使用路径产品复盘

复盘时间：2026-11-26（Asia/Singapore）
复盘对象：当前 `apps/selection-web` 工作台、任务队列和开源交付骨架
目标：让第一次使用的人能在明早完成“发起任务 → 看懂进度 → 打开报告 → 继续制作”，并在失败时知道如何恢复。

## 最高价值的可实施改进

### P0 · 入口必须可发现

1. **补齐主导航入口。** `AppShell` 的导航目前包含总览、报告、候选、资料包、制作档案、提示词、AI 整理提交和启动选品，但没有“调查报告”和“开发排期”。两个页面实际存在，用户只能依赖隐藏链接或直接输入 URL。明早至少把它们加入次级导航，或在主导航中加入“研究”和“排期”。同时给 `Active` 类型补上 `schedule`，避免排期页的 TypeScript 类型错误。
2. **首页首屏给出唯一下一步。** 当前首页内容丰富，但“启动一次选品”与“已有任务继续处理”分散在多个卡片。首屏应保留一个明显主按钮“启动选品”，旁边显示最近任务状态和最近报告链接。第一次使用不应先理解资源库、候选池和构建档案的关系。
3. **统一状态词。** 页面同时出现 `READY_FOR_BENCH`、`DRAFT`、`BUILDING`、中文状态和 `insufficient_data`。对用户显示中文状态，保留英文状态作为小字或详情字段，避免用户把资料包状态误认为任务完成状态。

### P0 · 任务失败必须可恢复

1. **前端提交必须带幂等键。** API 已支持 `Idempotency-Key` 和 `idempotencyKey`，但 `/selector` 当前提交请求没有带键。网络超时、用户重复点击或刷新后重试都可能产生重复任务。客户端应在一次提交前生成稳定键，直到收到任务 ID 前都复用该键，并在结果中标注“复用已有任务”。
2. **失败任务要有恢复动作。** 任务板目前只显示失败/阻塞原因。对 `failed`、`blocked` 和租约过期的任务应显示“重新排队”按钮，调用受控的重试 API，并明确递增尝试次数。没有权限时显示“联系管理员”，不要让用户只能复制任务号报障。
3. **显示租约和最后心跳。** `claimed/processing` 任务已有 `lease_expires_at` 和 Worker 标识，但任务板没有展示。增加“执行器、最后更新时间、租约剩余时间”能够区分正常长任务和卡死任务，也能降低重复点击与人工询问。
4. **任务详情需要事件时间线。** `GET /api/selection-requests?id=...` 已返回事件，UI 只显示单行状态。增加可展开的事件时间线，至少展示创建、认领、处理、复核、完成/阻塞和错误摘要。错误恢复必须以事件为事实来源。

### P0 · 完成含义要让用户看得懂

1. **`completed` 前显示门禁结果。** Worker 目前检查 YouTube 回执，报告 API 也做结构校验，但用户在任务板只看到“已完成”。报告页应显示“报告入库、视频证据、Feishu 回执”三个门禁小项，缺一项就显示“待复核”或“已阻塞”，避免把队列完成误读为研究完成。
2. **`insufficient_data` 需要下一步。** 候选详情已经能显示检索范围和限制，但缺少“补证动作”。至少显示检索词、检索时间、范围、限制和“重新补证/继续人工复核”的入口。`暂无视频` 不能替代可复核的限制说明。
3. **报告入口必须从任务板直达。** 已完成任务应把报告 ID 显示为可点击链接，点击后保留返回任务板的路径。当前链接只出现在状态小字里，长 ID 不利于扫描。显示报告标题和“打开报告 →”，把 ID 放在辅助文本。

### P1 · 信息架构与批量工作

1. **把“发起”和“处理”分成两个明确区域。** `/selector` 同时承载表单、自动轮询和历史任务。明早可保留单页，但应让“新建任务”与“任务队列”有明显标题锚点，并让状态筛选记住当前选择。后续可拆出 `/tasks`，把用户发起和维护人员处理分离。
2. **候选列表增加证据过滤。** 现在候选筛选支持路线、形态、决策、资料包、品类、市场和关键词，但没有 YouTube 状态过滤。增加“视频证据：已找到/检索不足”，让维护人员先处理证据缺口。
3. **制作档案与排期要串联。** `/schedule` 页面展示固定前 5 个 `READY_FOR_BENCH`，但没有对应制作档案入口和真实状态。每个排期卡应提供“打开制作档案”和“当前负责人”，并明确这是演示容量还是实际容量。

### P1 · 开源准备与首次启动

1. **根 README 增加 10 分钟启动路径。** 现有说明分散在根目录、`apps/selection-web/README.md` 和运维文档。开源用户需要一段从 `git clone`、`npm install`、环境变量、`npm test`、`npm run dev` 到提交一条本地任务的可复制步骤。
2. **明确本地与生产边界。** README 应把 D1/Cloudflare 依赖、Feishu 可选配置、Worker 手动命令、未启用 OIDC 的本地开发假设放在同一段。不要让“正式域名”“公开阅读”和“本地写入”看起来是同一个环境。
3. **提供安全的最小样例。** `.env.example` 只保留变量名和用途，附带无真实密钥的演示报告或 fixture。`LICENSE`、`CONTRIBUTING.md`、`SECURITY.md` 已存在，下一步在 README 顶部链接它们并说明外部服务凭据不应提交。
4. **补一份故障排查表。** 至少覆盖数据库未连接、任务一直 queued、租约过期、报告 JSON 校验失败、YouTube 回执缺失、Feishu disabled/发送失败和如何读取 `.worker-runs/<task-id>`。

## 明早可执行验收脚本

1. 用户打开 `/selector`，选择“宽泛选品”，输入一句要求，点击一次“启动选品”。
2. 模拟网络重试或连续点击，确认同一幂等键只有一条任务。
3. 任务板能看到 `queued → claimed → processing → review/completed` 的状态变化、更新时间和执行器。
4. Worker 失败时，用户看到明确错误、日志目录和“重新排队”入口。
5. 完成后点击“打开报告”，在候选详情看到 YouTube `found` 或 `insufficient_data` 的查询词、时间、范围和限制。
6. 从报告详情进入制作档案，再从排期页返回同一档案，链路不需要手工输入 ID。
7. 新用户按根 README 完成安装、测试和本地启动，不依赖生产域名、Feishu Webhook 或私人路径。

## 需要保留的边界

- OIDC、真实人员配置、自动分派容量、常驻 Worker、备份监控和正式域名属于生产门禁，不能用“页面可见”代替部署证据。
- Feishu 未配置时可以本地试用，但任务和报告必须明确显示 `disabled`，不能显示“已推送”。
- `READY_FOR_BENCH` 只能表示资料包完成门槛，不应被当作项目已上线或测试通过。

## 复盘结论

当前实现已经具备任务状态、租约、事件、YouTube 回执和失败可见性的基础。明早最值得优先补的是导航可发现性、客户端幂等键、失败重试入口、租约/事件展示和完成门禁摘要。这些改动会直接减少重复任务、状态误判和首次使用时的迷路。
