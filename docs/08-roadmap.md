# 路线图

## Spike（1 周）

- 固定状态机、容量公式和人员配置字段。
- 用内存/SQLite fixture 验证自动分派、认领、超时回收和全局上限。
- 用假研究适配器跑通 queued → completed 与 blocked。
- 为每个候选加入 YouTube 检索回执、图标/样图来源和页面视频入口；找不到时可复核地标记 `insufficient_data`。

出口：并发测试通过，任何任务都能解释“为什么分给谁/为什么没分”，每个候选都能解释“查过哪些 YouTube 视频/为什么没有可确认视频”。

## MVP（2–4 周）

- OIDC/账号、Postgres、Redis、API、任务列表、认领、人员配置。
- 接入一个研究适配器和一个执行器；报告入库、候选筛选、Feishu 卡片。
- 完成设计方向 A 的可用实现，保留 B/C 对比页面。

出口：10 个账号、100 个/日任务、备份和回滚演练通过。

## Pilot（2 周）

- 真实成员小范围使用，收集分派公平性、认领滥用、研究失败和报告质量。
- 增加租约回收、管理员重派、审计导出、成本和积压告警。

出口：完成率、P95 延迟、失败原因和容量利用率达到项目门槛。

## Production

- 绑定正式服务器、DNS、OIDC、Feishu 生产 Webhook。
- 研究适配器扩展到 Codex/OpenCode/Hermes，并按任务类型做预算与路由。
- 只在连续两个周期稳定后增加并发和数据连接器。
