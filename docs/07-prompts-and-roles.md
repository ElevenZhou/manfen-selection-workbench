# 角色与提示词系统

## 角色编排

| 角色 | 负责问题 | 输出 |
| --- | --- | --- |
| 项目经理 / COO | 目标、依赖、优先级和状态 | 任务合同、台账、交接 |
| 产品经理 | 用户任务、状态、指标和范围 | PRD、验收标准 |
| 研究经理 | 来源、证据、候选和缺口 | 研究包、来源账本 |
| 派发经理 | 人员、技能、容量和租约 | 分派决策、回收原因 |
| 技术经理 | API、数据、执行器和成本 | 技术方案、迁移、回滚 |
| 设计经理 | 三套方向、组件、状态和可用性 | 设计实验、选型记录 |
| 测试经理 | 正常、失败、越权、重试和恢复 | 测试报告、发布门禁 |
| 运维经理 | 服务器、备份、监控和事故 | Runbook、告警、演练 |

所有角色提示词都要求把事实、假设、推断、建议和阻塞分开；不把“已入队”“已领取”说成“已完成”。

## 统一输出协议

```json
{
  "status": "completed|partial|blocked|failed",
  "facts": [],
  "assumptions": [],
  "decisions": [],
  "evidence": [],
  "artifacts": [],
  "risks": [],
  "next_actions": [],
  "owner": "",
  "method_version": ""
}
```

## 提示词原则

1. 先读任务合同、项目资料、当前状态和权限，再行动。
2. 每个外部来源记录 URL、时间、范围、证据类型和局限；缺失时写 `insufficient_data`。
3. 不能绕过容量、权限、停止线、幂等、审计和人工复核。
4. 长任务按阶段回写心跳和产物，异常时停在 `blocked` 或 `partial`。
5. 任何代码变更都必须带测试、影响面、回滚方式和未验证项。

## YouTube 与视觉资料要求

研究经理对每个候选执行 YouTube 检索，至少覆盖候选名称、中文名称、唯一主竞品和玩法关键词。游戏候选必须检索实机、玩法演示、评测和宣传视频。每条视频保存具体 URL、标题、频道、发布时间、关联类型、检索时间和可访问性说明。

选品页面需要同时呈现候选图标、可用的参考产品图标或明确的生成图标状态，以及已核验的 YouTube 视频入口。视频不存在时显示检索结果和限制，不使用虚构链接或无来源样图。

所有开工提示词必须把 YouTube 检索列为首轮研究步骤，并把视频证据、视觉证据和缺口作为输入。没有 YouTube 检索回执时，提示词执行结果只能标记为 `partial` 或 `blocked`。
