# 选品系统 Web 化 UX 与质量路线（2026-11-11）

## 评审结论

现有 `site/` 已有稳定的公开档案产品骨架：总览、报告、研究、候选、资料包、排期、入库、启动选品，且视觉语言、路线色彩、跳过导航和基础焦点态已经统一。下一步不应继续堆页面，而要把“研究请求 → 证据 → 路线决策 → 资料包 → 开发台 → 结果回流”变成一条可追踪的操作流，并把 App、游戏、跨平台迁移和生活热点作为同一套对象模型下的不同工作模式。

主要 UX 风险：

- 导航是平铺的，用户无法快速区分“看结果”“做研究”“执行入库”三个工作区。
- 首页目前偏展示，缺少下一步动作、阻塞原因和最近活动；`SYSTEM READY` 不能代表数据真的可执行。
- 候选卡、报告详情和资料包之间的状态边界需要更明显，尤其要持续区分 `scouting_selected`、`route_selected`、`ready_for_bench`、`building`、`released`。
- 选 App、选游戏、跨平台迁移、日常热点需要在研究启动时选择工作模式，并在所有结果页显示该模式和证据截止时间。
- 公开阅读与管理写入应有不同的权限与反馈；入库、推送、排期等动作必须展示真实回执、失败原因和可重试入口。

## 信息架构与导航

将侧栏分成四组，保留现有路径兼容旧链接：

1. **驾驶舱**：总览、最近活动、异常与待处理。
2. **发现**：启动研究、趋势信号、调查报告、候选总表。
3. **决策与交付**：选品报告、资料包、开发排期、开发台、已发布。
4. **系统**：数据源、方法、结果入库、设置与审计日志。

桌面端侧栏显示分组标题；移动端改为底部 4 项主导航（驾驶舱、发现、交付、系统）并用抽屉承载次级页面。每页顶部保留面包屑、当前工作模式、数据截止时间和“返回上一步”。

新增全局状态条：`数据新鲜度`、`最近运行`、`待处理数`、`红灯数`。点击状态条进入过滤后的列表，避免用户靠猜测寻找阻塞。

## 核心操作流

### 1. 启动研究

启动页先选择工作模式：

- `APP_DISCOVERY`：移动 App 机会；
- `GAME_DISCOVERY`：游戏机会；
- `CROSS_PLATFORM_PORT`：将 Steam、桌面软件、主机或 Web 产品轻量化迁移到目标平台；
- `LIFE_HOTSPOT`：日常生活与时下热点。

随后填写方向、目标国家/平台、证据截止时间、预算/开发约束和期望产出。提交前展示“本次会生成什么”和数据源覆盖预览。提交后进入运行详情页，阶段为 `queued → researching → ranked → awaiting_review → archived/accepted`，每阶段带时间戳和日志摘要。

### 2. 证据审阅

运行详情采用三栏：左侧范围与假设，中部证据时间线，右侧候选排名。每条证据显示来源、采集日期、原始链接、证据类型、完整度和冲突提示。证据不足时允许“标记缺口”“保留观察”“加入下一期候选池”，禁止把研究建议直接变成路线入选。

### 3. 路线决策

候选详情页的决策头部固定显示：工作模式、`source_engine`、路线内排名、状态、方法版本、证据完整度和最近更新时间。所有操作按钮放在同一组：继续、返工、替换、停止、加入资料包。危险动作需要二次确认，确认文案中写明影响范围与是否产生新版本。

### 4. 交付与回流

资料包详情页用清单展示 8 组文件、缺失项、校验状态和下一步责任人；只有 `READY_FOR_BENCH` 才显示“领取开发台”。开发台与已发布页增加结果回流卡，允许录入版本、下载、留存、收入、停止原因，并链接回原候选和方法版本。

## 页面级改进

- **驾驶舱 `/`**：首屏增加“现在需要你处理的 3 件事”和异常列表；KPI 点击后带过滤条件；路线卡显示最终入选、备选、阻塞数量；增加最近运行时间和数据截止时间。
- **启动选品 `/selector`**：加入四种工作模式、范围模板、证据覆盖预览、幂等运行 ID 和提交后回执；保存草稿，避免长表单丢失。
- **调查报告 `/research`**：按模式、运行状态、证据完整度和是否进入路线池筛选；列表明确“研究建议/路线决策”层级。
- **选品总表 `/candidates`**：默认显示状态与模式筛选；支持保存视图、批量标记观察、导出当前证据索引；不提供跨路线混排总分。
- **报告详情 `/reports/[id]`**：顶部增加“数据范围/缺口”摘要和版本时间线；每个路线使用独立标签页，避免视觉上形成混合榜单。
- **资料包 `/packages`**：显示包完整度、阻塞文件、责任角色和最近校验时间；下载前展示清单哈希与版本。
- **排期 `/schedule`**：用泳道显示 `READY_FOR_BENCH → BUILDING → QA → RC → RELEASED`；拖动排期必须记录审计事件，不能修改路线结论。
- **入库 `/ingest`**：分为 JSON 校验、预览差异、提交、服务端回执四步；失败保留原始输入和可复制错误路径。

## 视觉与交互规范

保留现有深蓝底、米白纸张、A/B/C 路线色。新增工作模式使用独立图标和中性色，避免与路线颜色混淆。所有状态同时显示文字和颜色；红灯不能只靠颜色表达。表格在窄屏转为卡片，长链接折行，按钮最小触控区域 44px。图表必须显示单位、时间区间、来源和缺失数据；空状态给出下一步动作，加载状态显示阶段而非无限转圈。

所有写入动作遵循：操作前说明范围，提交后显示服务端回执，失败显示业务错误和重试条件。公开页面隐藏密钥、绝对路径和付费原始数据。键盘导航、跳过链接、焦点态、`aria-live` 回执和图表替代文本列入验收。

## Agent / MCP 的可见性

Agent 运行作为后台任务展示在“最近活动”中：任务名、触发人、开始时间、当前阶段、工具来源（MCP/API）、最后一条日志和产物链接。工具调用失败不得显示“已完成”；显示 `blocked` 及原因。允许用户暂停、重试或查看原始运行 ID。敏感参数只显示脱敏摘要。

## 验收门禁

1. 新用户能在 3 分钟内完成一次四种模式之一的研究提交，并看到运行 ID。
2. 从运行详情到候选、报告、资料包、排期、已发布，任一对象都能通过 ID 和版本时间线回溯。
3. 任何状态变更都有服务端回执；无回执时界面保持 `pending`。
4. App、游戏、跨平台迁移、生活热点四种模式均能生成同一结构的候选、证据、路线和资料包，并保留模式标签。
5. 路线 A/B/C 永不混排评分；跨路线页面只做排期和状态聚合。
6. 公开页面无密钥、Cookie、绝对路径；写入 API 有鉴权、幂等和审计事件。
7. 375px、768px、1440px 三种宽度下无横向溢出；键盘可完成主要操作；错误、空、加载、成功状态均可识别。
8. 运行 `npm test`、生产构建、路由冒烟和一次真实报告入库演练，保存截图、回执与版本号。

## 分阶段落地

- **Spike（1 周）**：统一工作模式字段、导航分组、运行状态条、启动页四模式和回执组件。
- **MVP（2–3 周）**：研究详情证据时间线、候选/资料包状态闭环、Agent 活动面板、排期泳道、审计日志。
- **Pilot（1–2 周）**：接入游戏与跨平台数据源，完成 4 种模式各 3 次运行；邀请协作者验证任务完成时间和错误恢复。
- **Production**：域名、HTTPS、备份、监控、错误告警、权限策略和回滚演练全部通过后再公开管理写入。

## 需要跟踪的产品指标

任务完成率、从研究提交到首次可审阅的时间、证据缺口率、候选进入 `READY_FOR_BENCH` 的比例、资料包返工率、从资料包到首次构建的时间、回流数据完整率、错误恢复成功率和四种模式的重复使用率。每项指标按工作模式与来源引擎分组，避免总体平均数掩盖某条路线或某个平台的问题。
