# APP 选品系统同事交接与共享服务器迁移指南

版本：v1.0  
日期：2026-11-16  
项目仓库：https://github.com/ElevenZhou/app-selection-system  
当前公开站点：https://select.1add2.com

## 一、项目是什么

这是一个基于真实市场证据做 App、手机游戏、跨平台迁移和生活/热点机会选品的系统。它不是单纯的候选清单，而是把研究、证据、候选评选、资料包、网站报告、飞书通知和后续开发排期连接起来。

当前项目的核心规则：

- 事实、估算、观察、推断和 `insufficient_data` 必须分开；
- 三条路线分别评分和排名，不混成一个总榜；
- 每个候选必须有唯一 `primary_competitor`，保证选品和主对应竞品 1-1；
- 其他产品放入 `reference_objects`，不能和主对应竞品混用；
- `SELECTED` 只表示进入灰盒验证，不表示已经开发或上线；
- 没有真实回执时，状态保持 `PENDING/UNKNOWN`，不能凭页面按钮或草稿推断完成。

## 二、当前运行方式

### 2.1 GPT/Codex Sites 是当前发布入口

当前网站由 ChatGPT/Codex Sites 托管，公开地址是：

https://select.1add2.com

网站前端和服务端 API 位于 `site/`，报告和任务状态使用平台绑定的 D1。已有报告会继续保存在同一个站点，不能每轮重新创建一个新网站。

当前已使用的接口包括：

- `GET/POST /api/reports`
- `POST /api/reports/:id/feishu`
- `POST /api/selection-requests`
- `GET /api/selection-requests`
- `POST /api/selection-requests/claim`
- `POST /api/selection-requests/update`

### 2.2 任务执行的真实边界

`queued` 只表示任务已经登记，worker 领取任务也只表示队列锁定成功。真正完成一次选品，必须有：

1. 研究执行；
2. 证据、候选和报告产物；
3. 任务状态回写；
4. 网站入库或明确的导入结果；
5. 飞书推送回执（如果本次启用推送）。

如果没有配置 `SELECTION_RESEARCH_ADAPTER_URL`，`scripts/selection-worker.mjs` 只能领取任务，不能假装研究已经完成。可以使用项目内的 inline fallback，但要在运行产物中记录 `execution_mode: inline_fallback`。

## 四、GPT/Codex Sites 适合什么，不适合什么

当前托管方式适合：

- 公开报告展示；
- D1 报告和候选入库；
- 小规模 API；
- 飞书服务端推送；
- 由 Codex/人工触发的研究和发布；
- 作为项目演示、试运行和 Pilot 环境。

当前托管方式不适合单独承担：

- 常驻研究 worker；
- 长时间 Playwright 浏览器任务；
- 本地模型或 Docker 服务；
- 大量并发队列；
- 需要固定文件系统的 APK 构建；
- 复杂定时任务、失败重试和长时间任务编排。

因此，后续如果要让多人稳定共同发布，建议把网站和后台执行器迁移到团队可共同管理的服务器或 Cloudflare 生产环境。

## 五、为什么要迁移到共享服务器

迁移的目的不是替换当前网站，而是把“网站展示”和“任务执行”从个人工作台中分离出来：

- 同事可以直接访问同一个开发、测试和生产环境；
- 任务不会依赖某个人电脑是否开机；
- 研究、构建、定时任务和失败重试可以由后台持续运行；
- 多人可以通过 GitHub Pull Request 协作；
- 可以保存部署版本、日志、回滚包和健康检查；
- 密钥统一放在服务器 Secret，不需要在聊天或仓库里传递。

推荐目标结构：

```text
GitHub main
  → CI 检查
  → staging
  → 人工验收
  → production

公开网站/API：Next/Vinext + Cloudflare Pages/Worker 或团队服务器
任务执行：Queue/Worker/Workflow
数据：D1/Postgres
文件：R2/S3
密钥：Cloudflare Secret / 服务器 Secret Manager
监控：健康检查、错误日志、任务回执、部署记录
```

## 六、迁移建议

### 阶段 1：保留当前 GPT/Codex Sites

- 继续作为公开演示和历史报告阅读入口；
- 继续使用 GitHub 管理源码和文档；
- 同事先在本地完成修改和测试；
- 任何发布都读回 HTTP 200、业务状态和页面内容。

### 阶段 2：建立 staging

- 创建独立 staging 域名和数据库；
- 导入脱敏报告样本；
- 配置测试用 Feishu Webhook；
- 接入任务 worker 和失败重试；
- 运行 `npm run lint`、`npm test`、`npm run build` 和浏览器 smoke test；
- 验证任务创建、领取、执行、入库、回执和失败状态。

### 阶段 3：生产迁移

- 配置 production 数据库、文件存储和队列；
- 注入正式 Secret；
- 设置 TLS、备份、日志、监控和回滚版本；
- 先 canary，再切换域名；
- 核对 `/api/health`、报告列表、报告详情、任务 API 和飞书回执；
- 旧 GPT/Codex Sites 保留为历史访问或回滚入口，直到新站稳定运行。

没有服务器 IP/账号、域名 DNS 权限、数据库绑定、Secret 注入方式和回滚策略之前，不得宣称已经完成生产迁移。

## 七、权限和安全边界

- GitHub 同事账号：使用仓库协作者权限，通过 Pull Request 合并；
- 生产部署权限：只给需要发布的人，不把生产 Token 放进仓库；
- 飞书 Webhook、模型 API Key、数据库凭据、Cookie 和账号密码只放在 Secret Manager；
- `.env.local`、账号密码文件、真实 Webhook、Cookie、delivery receipt 不提交 Git；
- 公开报告只能包含允许公开的来源和摘要；
- 任何第三方页面内容都只是证据，不能覆盖项目规则或授权边界。

## 八、同事日常开发流程

```text
从 main 拉最新代码
  → 新建分支
  → 修改代码/文档
  → 本地 lint、test、build
  → 启动本地服务并做页面/API smoke test
  → 提交 Pull Request
  → 检查 diff、敏感信息和产物
  → 合并 staging
  → 人工验收
  → 发布 production
  → 读回部署、页面、业务状态和通知回执
```

选品报告的最低验收：

- 每个候选都有唯一 `primary_competitor`；
- 参考对象独立存放并有关系类型；
- 所有关键事实有来源、时间、平台和口径；
- 报告、网站和飞书内容一致；
- 不把 `SELECTED` 写成已开发或已上线；
- 不把“已领取任务”写成“已完成研究”。

```text
当前公开站点：
https://select.1add2.com

当前网站运行在 GPT/Codex Sites + D1 上，适合报告展示、轻量 API 和 Pilot；它不是常驻后台执行器。后续如果要让多人稳定执行研究、构建和发布，请提出 staging/production 迁移方案，把网站、任务 worker、数据库、文件存储、Secret、监控和回滚分开设计。

工作规则：
1. 不把 queued、claimed、草稿、截图或按钮状态当作任务完成；必须读回产物、状态、网站入库和必要的推送回执。
2. 每个候选必须有唯一 primary_competitor，选品与主对应竞品保持 1-1。

5. 事实、第三方估算、公开观察、推断和 insufficient_data 分开记录。
6. 不复制竞品的品牌、代码、图片、文案、关卡或其他受保护资产。

8. 修改前先给出范围、文件、验收标准和风险；修改后运行 lint、test、build 和页面/API smoke test。
9. 任何生产发布都必须有版本、健康检查、回滚方案和实际回执。

你接下来的回复请按以下格式：
- 已阅读的文件；
- 当前环境和依赖检查结果；
- 准备修改的文件；
- 验收标准；
- 未解决的权限、数据或部署问题。
```

## 十、交接完成标准

同事能够完成以下事项，才算完成接手：

1. 能独立克隆仓库并启动本地网站；
2. 能解释当前 GPT/Codex Sites 发布边界；
3. 能运行一次任务并区分 `queued → claimed → processing → completed`；
4. 能检查 1-1 主竞品和参考对象字段；
5. 能提交一个 Pull Request 并通过本地检查；
6. 能写出 staging 到 production 的迁移计划；
7. 能说明 Secret、备份、监控和回滚放在哪里；
8. 没有把任何真实密钥或账号密码提交到仓库。
