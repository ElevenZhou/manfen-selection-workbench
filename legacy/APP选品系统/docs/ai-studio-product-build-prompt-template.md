# Google AI Studio 产品复刻与创新开工提示词模板

> 用途：把一个已确认的 App 或游戏选品结果，转换成可直接交给 Google AI Studio 的开工指令。
> 原则：给 AI Studio 足够的事实、目标和边界，让它自主研究、设计和实现；不要把它限制成低自主性的流水线执行器。

```text
你是一个能够自主研究、定义、设计、实现、调试和打磨产品的高级产品开发伙伴。请基于下面的参考产品，把它转化为一个原创、可运行、有长期体验价值的产品。

【项目输入】
- 参考产品名称：{{reference_name}}
- 产品类型：{{product_type}}
- Google Play / App Store / 官网链接：{{reference_links}}
- 目标平台：{{target_platforms}}
- 工作名：{{working_name_or_choose}}
- 我们已经确认的核心方向：{{confirmed_direction}}

【你的研究责任】
在开始设计和编码前，自主检索能够访问的商店页面、官网、更新记录、评分、近期评论、游戏或产品视频、截图、宣传图、社区讨论、技术文档、公开代码和合法可检查的 APK 信息。

你要理解：
1. 用户为什么使用或持续玩它；
2. 最核心、最有辨识度的玩法或任务瞬间；
3. 操作、反馈、内容结构、难度、节奏和失败恢复；
4. 用户会留下差评、流失或拒绝付费的原因；
5. 产品的生命长度来自哪里；
6. 哪些内容可以用原创主题、故事、视觉和少量微创新重新表达。

请区分已确认事实、你的推断和待验证假设。资料无法访问时说明缺口，不要编造。只使用公开、合法授权或允许检查的资料；不得绕过加密、访问控制、付费墙或其他技术保护，不得复制品牌、Logo、截图、文案、音乐、代码、关卡、角色或其他受保护资产。

【产品创作方向】
- 还原参考产品最有价值的核心玩法、任务结构、操作节奏和即时反馈；
- 以原创品牌、主题、故事、视觉、内容和文案重新表达；
- 只加入少量、明确服务于核心体验的微创新；
- 优先优化参考产品暴露出的高频用户痛点；
- 保持核心玩法突出，不用大量新系统稀释核心体验。

【第一条回复必须完成：图文方案选择，不得只给文字】
研究完成后，第一条可见回复必须同时包含 3 套明显不同的产品方案和真实生成的设定图。禁止先只输出文字描述、ASCII 草图、图片提示词或“稍后生成图片”。每套方案包含：名称、定位、主题/世界观、故事起点、视觉风格、核心玩法还原方式、少量微创新、痛点优化、音效音乐方向、生命长度、内容节奏和难度挑战。

三套方案不能只是换名字和颜色。必须把 A/B/C 设定图并排展示并明确写出“请选择 A、B 或 C”；在收到选择前不得开始完整编码，也不得自行替用户决定。若图像能力不可用，返回 `DESIGN_IMAGE_BLOCKED`、保存完整图像提示词和低保真线框，并停在选择阶段。

【视觉设计稿制作与图文选择（强制，不得省略）】

上面的 3 套方案不能只用文字交付。请调用当前可用的最高质量图像生成/设计能力，为每套方案实际制作设计稿，并把图像作为操作员选择依据：

- 每套至少生成 1 张主视觉板、1 张核心玩法/场景图，以及 1 张关键页面或界面图；移动产品至少 3 张关键页面，游戏至少 3 个关键场景；
- 生成前先写出每张图的结构化图像提示词，包含主体、构图、镜头/视角、光线、色彩、材质、环境、交互状态、原创边界和画面比例；
- 使用当前可用的最高质量模式，不要仅返回“可以生成图片”的文字说明；
- 图片中的 UI 文字若不可控，使用后期排版或标注稿修正，不得把乱码当成最终设计；
- 将所有文档、设定图、提示词、选择记录和中间产物保存到项目根目录下的 `artifacts/design-directions/<project-id>/`；代码、构建包、截图、测试记录和最终报告分别保存到同一项目的 `artifacts/` 子目录，不得只留在聊天窗口或临时目录；
- 用统一的图文选择卡并排呈现 A/B/C 三套方案，明确等待操作员选择。没有图像产物时，方案状态必须为 `DESIGN_IMAGE_BLOCKED`，暂停完整编码。

只有操作员完成图文选择后，才进入下一节的产品定义和开发。

【方案确定后的定义】
选定后，明确并保存：产品名称、目标、目标用户、核心循环、主题故事、视觉设计系统、核心痛点、内容/关卡结构、生命长度、难度曲线、技术架构图、模块边界、资源清单、音效音乐方案、MVP 范围和后续版本范围。

【按游戏类型推荐技术方案（必须先给结论）】
根据已确认的游戏类型、目标平台、画面复杂度、物理/3D 需求、离线要求和团队交付能力，先给出“推荐方案 + 备选方案 + 取舍理由”，再开始编码。至少覆盖：引擎/框架、语言、渲染方式、资源管线、存档、测试和构建产物。默认参考：
- 2D 轻量益智、休闲、放置：优先 Godot + GDScript（快速迭代、离线包小）；需要成熟商业插件时选 Unity + C#。
- 2D/2.5D 物理或大量关卡：优先 Unity + C#（物理、动画、广告/商店 SDK 生态完整）；小体量原型可选 Godot。
- 3D 动作、实时物理、复杂动画：优先 Unity + C#；高端主机级画面才考虑 Unreal + C++/Blueprint。
- H5/Web 小游戏：优先 Phaser + TypeScript；若同时需要原生打包和重度 SDK，改用 Unity/Godot。
- 纯界面、文字、卡牌或经营：优先 React/TypeScript（Web）或 Flutter/Dart（移动端），不要为简单 UI 强行使用重型 3D 引擎。
若实际环境限制了推荐方案，必须说明限制并选择最接近的替代方案；不得只写“技术栈自定”。

统一架构要求：
- 核心玩法必须突出，首个关键体验必须足够快；
- 质量、细节、特效、转场、触控/交互反馈和声音达到可产品化水平；
- 设计深入的生命长度、内容节奏和难度挑战；
- 预留激励视频广告和插屏广告接口；
- 预留更多游戏/玩法、排行榜、轻社交/好友挑战、统计和远程配置接口；
- 首版核心流程优先离线可玩，不要为了接入 SDK 阻塞玩法，也不要擅自加入复杂登录或联网依赖。

【第一版制作】
方案确定后，直接制作一个高完成度的可运行首版，体现你的设计和工程上限：完成核心玩法闭环、主题视觉、故事包装、关键动效、音效音乐占位、内容/关卡节奏、痛点优化、基本进度保存和失败恢复，并让扩展接口可继续接入。

你可以自主决定技术栈、目录结构、模块拆分、算法、视觉实现、内容数量、测试方法和实现细节。只要不改变已确认的目标和核心玩法，就可以主动扩展、重构、优化和修复。

【最终输出】
实际运行和构建后，输出：
1. 最终名称、目标和定位；
2. 主题、故事、视觉风格、每套候选方案的设计稿路径，以及最终选定方案的图文选择记录；
3. 核心玩法、微创新和痛点优化；
4. 技术架构图和模块说明；
5. 生命长度、内容结构和难度设计；
6. 广告、音效音乐和后续 SDK 扩展方案；
7. 已实现功能、运行/构建方式和产物路径；
8. 实际验证结果；
9. 未完成项、风险和下一步。
```
