# 选品系统扩展产品路线图（2026-11-11）

## 目标

把现有“App 竞品选品 + 资料包 + 网站发布”扩展为一个统一机会操作系统，支持三类对象：移动 App、手机游戏、跨平台迁移机会，以及日常生活和时事热点驱动的创新机会。底层使用同一套“用户任务—证据—替代方案—改进结果—验证门槛”模型，评选路线和对象类型保持可区分，避免把不同证据混成一个排行榜。

## 统一机会模型

每个机会都由以下六层组成：

1. **对象层**：`product_form`（mobile_app、mobile_game、web、desktop、cross_platform_port、daily_life_solution）和原平台/目标平台。
2. **任务层**：目标用户、触发场景、核心任务、期望结果、当前替代方案。
3. **证据层**：市场/商店指标、评论与痛点、搜索与热点、社区行为、技术变化、人工流程或实地观察；每条证据保留来源、时间、国家、可信度。
4. **创新层**：精简、迁移、重组、本地化、AI 自动化、成本下降、可达性改善等创新动作，限制为 1–3 个核心改变。
5. **验证层**：前置实验、原型、落地页、人工服务、试用、留存/付费指标和停止条件。
6. **经营层**：目标渠道、商业化、开发复杂度、合规/IP 风险、单位经济和发布后结果。

建议新增字段：`source_platform`、`target_platform`、`portability_reason`、`legal_ip_status`、`task_frequency`、`pain_severity`、`evidence_freshness`、`validation_stage`、`risk_flags`。跨平台机会必须明确“功能/交互启发”与“代码、素材、商标、内容授权”的边界。

## 四类发现路线

### A. App 与游戏验证型

沿用 Engine A，增加游戏专属证据：核心循环、首局时长、失败/奖励机制、广告频率、关卡更新、社交/竞技结构。App 和游戏分开排名，但共享竞品、评论、收入和留存字段。

### B. 跨平台迁移型

研究 Steam、主机、桌面软件或复杂 Web 工具，判断是否能在 Android/iOS/Web 形成轻量版本。每个候选必须回答：移动端最小任务是什么、哪些能力可以删减、输入和性能如何重做、离线/隐私如何处理、是否存在授权或 IP 障碍。评分维度：任务强度、迁移后结果改善、目标设备可行性、用户获取、授权/IP 风险、开发成本。

### C. 日常生活重构型

围绕高频、重复、耗时或易出错的生活任务，使用 Engine B 的第一性原理流程。证据可来自真实工作流、服务价格、社区求助、评价、线下观察和小实验。热点只能作为研究触发器，必须补足稳定任务证据。

### D. 热点趋势型

沿用 Engine C，新增“事件到任务”转换：热点 → 受影响人群 → 新增任务/约束 → 可持续需求 → 可触达渠道。对短期事件设置有效期、复查日期和停止条件，避免把一次性流量当长期产品机会。

四条路线各自输出 `SELECTED / BACKUP / WATCH / REJECTED`，不生成跨路线总分。网站允许跨路线浏览，但每个排名必须带 `source_engine` 和 `method_version`。

## 网站信息架构

保留现有 `/`、`/reports`、`/candidates`、`/packages`、`/schedule`、`/ingest`，新增或升级以下页面：

- `/opportunities`：统一机会总表，支持对象类型、来源平台、目标平台、路线、国家、验证阶段、风险和新鲜度筛选。
- `/opportunities/[id]`：机会详情，按“任务—证据—竞品/替代—创新—验证—经营”展示，并显示状态机和证据缺口。
- `/games`：游戏专属漏斗、玩法标签、核心循环和留存/变现对比。
- `/porting`：跨平台迁移工作台，展示源产品、目标平台、可删减模块、技术/授权风险和迁移实验。
- `/signals` 与 `/signals/[id]`：热点、搜索、社区、技术和政策信号；显示持续性、独立来源和任务转化状态。
- `/life`：日常生活机会池，按频次、痛点、替代成本和可触达性排序。
- `/experiments`：前置验证实验、样本、结果、下一步和停止记录。
- `/methodology`：对象与路线方法版本、阈值、字段解释和证据等级。
- `/admin/sources`：数据源健康、配额、更新时间、错误与人工复核队列。

驾驶舱首页增加四个分区：本周 App/游戏、跨平台迁移、日常生活、热点雷达；每区显示候选数、证据完整度、待验证数、红灯数和最近结果。统一搜索支持名称、任务、平台、来源和标签。

## 核心流程

```text
输入（自然语言/URL/文件/API/热点）
  → 规范化对象与任务
  → 路由到 App、游戏、迁移、生活或热点路线
  → 采集并登记证据
  → 形成候选与竞品/替代方案组
  → 独立评分、门槛检查和人工决策
  → 生成资料包与验证实验
  → 网站入库、通知、开发排期
  → 发布结果回流，校准评分和来源
```

状态必须分层：`SCOUTING` → `EVIDENCE_READY` → `ROUTE_SELECTED` → `EXPERIMENT_READY` → `READY_FOR_BENCH` → `BUILDING` → `RELEASED` → `STOPPED`。任何 `WATCH` 或热点草案都不能直接进入开发台。

## 分阶段交付

**Spike（1–2 周）**：扩展 Schema、对象/平台标签、统一候选表和迁移/游戏/生活四个示例报告；完成只读页面和筛选。

**Demo（2–3 周）**：实现 `/opportunities`、详情页、信号页、实验页；接入已有报告 JSON/CSV；支持人工导入和状态变更。

**MVP（4–6 周）**：完成四路线运行合同、资料包模板、证据缺口校验、网站 API、审计日志、飞书摘要和基础权限。

**Pilot（6–8 周）**：选 1 个游戏、1 个 Steam→Android 迁移、1 个生活任务、1 个热点机会做闭环；记录研究耗时、证据完整度、实验转化和发布结果。

**Production**：部署到现有站点或独立域名，配置环境变量、备份、监控、回滚和域名解析；通过真实运行回流校准阈值后再扩大数量。

## 验收标准

- 同一候选可被标记为 App、游戏或迁移机会，且原/目标平台字段完整。
- App、游戏、迁移、生活、热点路线可独立运行、独立排名、独立导出。
- 每个候选至少有一条可点击来源、证据时间和可信度；缺口明确显示 `insufficient_data`。
- 跨平台候选有可删减模块、目标设备约束、IP/授权状态和停止条件。
- 热点候选有持续性、任务转化和复查日期；短期热点不会自动进入开发。
- 网站筛选、详情、状态流转、实验记录和报告导出可通过浏览器完成。
- 网站公开内容不包含 Token、Cookie、付费数据原件或本机绝对路径。
- 现有历史报告、资料包和 URL 保持可访问，新增功能不改变既有路线评分。
- 至少完成一次端到端 Pilot，并读回网站入库、状态变更、实验结果和通知回执。

## 关键风险与决策门

IP/授权、商店政策、数据供应商成本、热点噪声和跨平台性能是四类主要风险。任何风险未解决时，候选只能保持 `WATCH` 或 `EXPERIMENT_READY`。部署、域名切换和外部账号配置属于独立变更，必须在本地验证、备份、canary 和回滚方案齐备后执行。
