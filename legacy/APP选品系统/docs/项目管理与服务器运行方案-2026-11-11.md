# 项目管理与服务器运行方案

日期：2026-11-11

## 结论

当前系统已经能完成选品、资料包生成、网站入库和排期展示；但“每个最终选品是否已经开发、是否已上架”目前没有真实开发台/商店回执接入，不能仅凭 `READY_FOR_BENCH`、`BUILDING` 或排期记录判断已完成。必须新增项目管理与发布证据层。

目标运行方式：

```text
服务器 Web + Worker/队列 + D1/数据库
  → 服务端模型 API Key / 外部数据 API Key
  → Agent/MCP 执行器
  → 项目管理与提醒
  → 开发/QA/发布回执
  → 公开网站展示脱敏结果
```

本机 Codex 继续作为管理和开发入口，但不再是生产运行依赖。服务器上的服务只读取服务端 Secret，不把 Key 返回浏览器。

## 一周一个可验收版本

每个项目从周一开始，周日形成版本回顾；开发期不再按“无限期排期”管理。

| 日期 | 阶段 | 必须产物 | 负责人动作 |
|---|---|---|---|
| 周一 | 启动 | 项目卡、资料包校验、范围冻结 | 产品负责人确认目标与非目标 |
| 周二 | 设计/技术 | 页面稿、技术方案、风险清单 | 设计/技术负责人签收 |
| 周三 | 核心开发 | 可运行主流程 | 开发负责人提交 commit/build |
| 周四 | 完整流程 | 关键异常、数据、埋点 | QA 开始验收 |
| 周五 | RC | RC 包、截图、测试记录 | 项目负责人决定修复或候选发布 |
| 周六 | 发布准备 | 商店素材、隐私、版本号、回滚包 | 发布负责人检查门禁 |
| 周日 | 复盘 | 上线回执或阻塞单、下周计划 | 总控更新状态和方法反馈 |

“一周完成”定义为：完成一个可验证的版本或明确记录阻塞原因，不等同于商店审核必然在一周内通过。

## 项目状态

```text
ROUTE_SELECTED
→ READY_FOR_BENCH
→ PLANNED
→ IN_PROGRESS
→ INTERNAL_TEST
→ QA
→ RC
→ RELEASE_SUBMITTED
→ RELEASED
→ MONITORING
→ STOPPED / BLOCKED
```

每次状态变化必须保存：操作者、时间、版本、证据 URL/文件、下一步、截止时间和阻塞原因。

## 项目管理实体

新增或扩展：

- `projects`：项目主卡、候选 ID、产品形态、源/目标平台、负责人、优先级、截止日期；
- `project_members`：产品、设计、开发、QA、发布、增长负责人；
- `project_tasks`：任务、状态、依赖、截止日期、提醒规则；
- `project_events`：状态变更、评论、审批、回执和审计；
- `release_evidence`：构建号、版本号、测试报告、商店 URL、审核状态、上线时间；
- `notification_channels`：Feishu/Webhook/Email 等地址及事件过滤；
- `reminder_rules`：逾期、无更新、阻塞、发布失败、数据异常规则。

## Web 操作台

新增 `/projects`、`/projects/[id]`、`/projects/[id]/timeline`、`/releases`、`/settings/notifications`：

- 项目列表：按负责人、状态、截止日期、产品形态、是否已发布筛选；
- 项目详情：一周目标、任务清单、负责人、风险、回执和时间线；
- 发布页：区分“已提交审核”“审核通过”“已上架”“已验证可访问”；
- 通知设置：Webhook 地址只显示掩码，保存后做一次验证并记录回执；
- 总览页：同时显示选品数量、开发中、QA、RC、已提交、已上架、最近回流结果。

## Webhook 事件

建议事件：

- `project.created`
- `task.overdue`
- `project.blocked`
- `build.completed`
- `qa.failed`
- `rc.ready`
- `release.submitted`
- `release.approved`
- `release.published`
- `release.verification_failed`
- `feedback.updated`

Webhook 发送必须有幂等键、签名、重试上限、响应状态、业务 code 和投递记录。没有成功回执时保持 `PENDING`，不能显示“已通知”。

## 服务器与 API Key

推荐先采用：

- Web：现有 Next/Vinext；
- 数据：D1/Drizzle；
- 长任务：Worker + 队列；
- Secret：平台 Secret/Secret Manager；
- 反向代理：TLS、健康检查、访问日志、限流；
- 环境：staging 与 production 分离。

服务端 Secret 示例：

```text
MODEL_API_KEY=<server secret>
MODEL_PROVIDER=<provider>
FEISHU_SELECTION_WEBHOOK_URL=<server secret>
APP_MARKET_API_KEY=<server secret>
WEB_TRAFFIC_API_KEY=<server secret>
PROJECT_WEBHOOK_SIGNING_SECRET=<server secret>
```

禁止：把 Key 写进 `.env` 提交、前端 bundle、报告 JSON、截图、飞书卡片或浏览器响应。

## 上线验收

只有同时读到以下证据，才标记 `RELEASED`：

1. 构建成功与版本号；
2. QA 通过记录；
3. 发布平台提交回执；
4. 发布平台审核/上架回执；
5. 真实商店或下载地址 HTTP/页面可访问验证；
6. 版本、时间和项目 ID 能回链；
7. 监控与回滚信息已保存。

若只有资料包、排期、截图或“准备发布”，状态保持 `READY_FOR_BENCH`、`IN_PROGRESS`、`RC` 或 `RELEASE_SUBMITTED`，不得升级为已上线。

## 当前迁移顺序

1. 先建立项目主卡、负责人、状态和一周任务模板；
2. 接入开发/QA/发布回执；
3. 接入 Webhook 和逾期提醒；
4. 在 staging 配置模型 API Key；
5. 通过一条真实项目跑完整链路；
6. 再切 production 和域名。
