# 联网大模型现查研究协议与运行产物规范

> 版本：v1.2  
> 生效日期：2026-07-25  
> 适用范围：全市场、专项、即时和复评选品运行

## 1. 结论

当前数据采集层不建设持续网页爬虫。每次选品由联网大模型接收严格的研究任务合同，现用现查官方商店、产品官网、公开排行榜、第三方行业报告、用户评论、社区讨论、GitHub、搜索趋势、流量和技术发布信息。

这不意味着“让模型自由发挥”。模型必须执行固定研究协议，输出可复核证据账本。模型记忆、无链接数字、搜索摘要和二次转述不能单独支持入选。

## 2. 来源优先级

1. 官方商店、产品官网、价格页、发布说明、帮助中心、官方开发者文档。
2. 有明确口径的 App 市场、流量、搜索、广告或游戏数据平台。
3. 近期商店评论、支持社区、Reddit、专业社区和公开用户讨论。
4. GitHub 仓库、Release、Issue、Contributor 和官方趋势页。
5. 新闻、目录和社交帖子只用于发现线索，必须交叉验证。

精确下载、收入、活跃、留存或流量数据不可得时：

- 不推算伪精确数字；
- 使用商店下载档位、评论量、排名、更新频率和多来源相对趋势作为代理指标；
- 把字段标为 `unknown`、`estimate` 或 `observed`；
- 降低置信度并记录最便宜的补证方式。

## 3. 专业研究提示词

以下提示词由 Evidence、Signal Radar 或路线 Skill 填充后交给具备联网能力的大模型：

```text
你是 App 市场证据研究员。你的任务不是生成创意，而是为一次可审计的选品决策建立事实底座。

研究目标：
- run_id: {{RUN_ID}}
- 路线: {{ENGINE_A_OR_B_OR_C}}
- 方向: {{DIRECTION}}
- 市场/国家: {{MARKETS}}
- 商店/平台: {{PLATFORMS}}
- 时间截止: {{DATA_CUTOFF}}
- 需要的合格数量: {{QUALIFIED_COUNT}}

强制规则：
1. 必须联网现查。不得把模型记忆写成当前事实。
2. 先建立足够宽的发现池，再按所属路线方法评选；不得先定答案再找证据。
3. 每个关键事实记录：claim、entity、country、platform、period_start、period_end、
   collected_at、value_type、source_name、source_url、confidence。
4. 数字必须带口径、地区、平台、时间和来源。无法确认时写 unknown，禁止补数。
5. 官方事实、第三方估算、公开观察、内部数据和假设必须分开。
6. 至少交叉两类独立来源。来源冲突时保留双方、解释差异，不擅自取平均。
7. 用户价值和用户痛点必须分别有证据；短摘录仅保留表达主题所需内容。
8. Engine A 至少三个真实直接竞品；Engine B 至少三个替代方案或 workaround；
   Engine C 至少三个独立领先信号，并补一个真实行为、替代行为或实验方案。
9. 每个候选只给一到三个结果型改变；不得用“增加 AI 聊天”代替产品改进。
10. 游戏市场数据只证明品类有人尝试或付费；入选仅代表进入灰盒验证，
    未经玩家测试不得宣称玩法好玩。
11. 为每个候选判断 `product_form` 和真实目标平台；为每个参考对象判断 `entity_kind`。
12. 每个候选必须有唯一 `primary_competitor`；其他产品放入 `reference_objects`。主对应竞品与候选保持 1-1，不能用通用竞品数组覆盖多个候选。
13. 检查名称、商店链接和来源链接是否可访问。真实移动 App / 游戏必须优先记录官方商店链接；非 App 对象的 `store_url` 必须为空，并记录官方页或证据来源。
14. 分类与链接规则遵循 `docs/14-产品形态与参考对象分类规范.md`。
15. 达不到门槛就少选，不能为了数量伪造证据或提高完整度。

输出：
- queries.json：实际执行的查询、目标来源和查询时间；
- sources.json：去重后的来源清单；
- evidence.json / evidence.csv：逐条事实与观察；
- review-themes.csv：价值、痛点和请求主题；
- candidates.json / candidates.csv：路线内评分、排名和决定；
- report.md：结论、依据、改进、风险、缺口和下一步验证；
- qa.json：链接、字段、门槛、冲突和数量检查结果。
```

## 3.1 任务领取与执行状态

任务被 `/api/selection-requests/claim` 领取，只代表队列锁定成功，不代表研究已执行。执行器必须继续完成研究、生成产物、回写状态并读回结果。若 `SELECTION_RESEARCH_ADAPTER_URL` 未配置，worker 只能报告 capability gap；可以由项目内 inline fallback 继续执行，但必须在运行产物中记录 `execution_mode: inline_fallback`。没有报告产物、任务回写和必要的入库/回执，不得将状态写成 `completed` 或 `published`。

## 4. 查询策略

每个候选至少覆盖四类问题：

1. **存在性**：产品是否仍可用、市场和平台是什么、最近是否更新。
2. **需求性**：下载档位、评论量、排名、搜索、讨论、流量或公开采用证据。
3. **问题性**：近 90 天及较长窗口的重复价值、痛点、价格、广告、隐私和故障。
4. **可执行性**：一到三个改变是否可在最小版本验证，是否涉及受保护资产或高风险能力。

查询必须保存，而不是只保存最终链接。建议组合：

```text
<产品名> official app store pricing release notes
<产品名> reviews complaint feature request 2026
<品类> downloads revenue growth 2025 2026 report
site:play.google.com/store/apps <关键词>
site:apps.apple.com <关键词>
site:github.com <技术或任务>
site:reddit.com <用户任务或失败结果>
```

## 5. 不可覆盖的 Run Bundle

每次运行建立一个独立目录：

```text
outputs/selection-runs/<run_id>/
├── 00-run/
│   ├── contract.json
│   ├── ledger.md
│   └── qa.json
├── 01-research/
│   ├── queries.json
│   ├── sources.json
│   ├── signals.json
│   ├── evidence.json
│   ├── evidence.csv
│   └── review-themes.csv
├── 02-routes/
│   ├── route-a.json
│   ├── route-b.json
│   ├── route-c.json
│   ├── candidates.json
│   └── candidates.csv
├── 03-report/
│   ├── report.md
│   └── selection-table.csv
├── 04-packages/
│   └── <package_id>/
├── 05-publish/
│   ├── website-report.json
│   └── import-receipt.json
└── 06-schedule/
    └── development-queue.csv
```

规则：

- `run_id` 一经使用不覆盖；修订创建 `-v2`。
- JSON 是机器事实源，Markdown 和 CSV 是阅读视图。
- 资料包目录是开发台原件；同时生成 ZIP、SHA-256 和相对下载地址。
- 网站展示报告与资料包摘要，提供详情、复制开发提示词和 ZIP 下载。
- 生产网站不展示本机绝对路径；本地路径仅写入内部台账。
- 只有资料包文件真实存在、Schema 通过且 ZIP 校验完成，网站才能显示 `READY_FOR_BENCH`。
- QA 必须检查产品形态、目标平台、参考对象类型和链接语义一致；分类缺失、移动 App 缺官方商店链接、非 App 伪造商店链接均不得通过。

## 6. 网站与本地的职责

- 本地 `outputs/selection-runs/`：完整研究证据、内部台账和开发台原件。
- 统一网站：公开地址 <https://select.1add2.com>；展示报告时间线、选品总表、来源链接、候选详情、资料包状态与允许公开的下载物。
- 网站数据库：可查询的报告和候选元数据。
- 静态文件或对象存储：允许公开的 ZIP；有授权数据时只放许可后的摘要，不放原始付费导出。

公开发布前必须执行敏感信息检查：不得包含 Webhook、Token、Cookie、供应商密钥、个人隐私、付费数据原件或本机绝对路径。公开网站的匿名可读性与服务端写操作权限必须分离。

## 7. 何时才需要 API 或采集服务

满足任一条件再评估稳定接口：

- 同一来源每周重复人工查询，成本持续上升；
- 需要历史快照计算增速，而公开页面没有历史；
- 需要可复现的国家、榜单或竞品批量比较；
- 商业数据供应商已经提供合法、稳定、成本可接受的 API 或导出。

优先级是：官方 API或授权导出 → 商业数据接口 → 浏览器现查 → 最后才考虑合规的定向采集。持续爬虫不是当前默认方案。
