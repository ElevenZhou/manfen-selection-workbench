# 选品综合数据看板与开源项目评估

日期：2026-11-11

## 结论

建议采用“自研选品驾驶舱 + ECharts + 独立指标层”的方案，暂不把 Metabase、Superset 或 PostHog 直接当作主产品界面。

第一阶段：现有 Next/Vinext 网站内嵌 Apache ECharts，直接服务 D1/Drizzle 的聚合 API。  
第二阶段：当历史证据、运行事件和发布结果增长后，引入 ClickHouse 作为分析库，保留 D1 作为事务库。  
第三阶段：引入 Cube Core 或 Lightdash 作为指标/语义层，让 Web、MCP 和 AI Agent 读取同一套指标定义。

## 推荐项目

| 项目 | 适合位置 | 优点 | 当前限制 | 建议 |
|---|---|---|---|---|
| Apache ECharts | 前端图表层 | Apache 2.0、React 可用、交互图表丰富、适合现有 UI | 不负责数据建模、权限和指标治理 | 立即采用 |
| Cube Core | 指标层/API 层 | 开源语义层，可通过 SQL、REST、GraphQL 给 BI、应用和 AI Agent 使用 | 需要单独服务和生产鉴权；开发模式不能暴露公网 | MVP 后评估 |
| ClickHouse | 分析数据库 | 面向实时分析和大规模聚合，适合时间序列、漏斗、分组和高频事件 | 需要独立运维、同步和备份 | 数据量上升后采用 |
| Apache Superset | 内部分析后台 | 开源 BI、探索、Dashboard、REST API、语义层能力 | UI 与现有产品不一致，嵌入和权限运维复杂 | 作为内部专家工具 |
| Lightdash | dbt/指标治理 | 指标和 Dashboard 可代码化，并支持 Agent、MCP、嵌入 | 偏现代数据栈，需要 PostgreSQL/仓库和 dbt 习惯 | 团队需要治理时评估 |
| PostHog | 产品行为分析 | 自托管事件分析、漏斗、留存、功能使用和实验 | 不是选品证据库；自托管有较重运维 | 用于网站/已发布产品行为，不作为选品主库 |

## 为什么不是直接上 BI 工具

你们的看板不是普通经营报表，而是要回答：

- 哪类机会在不同周期持续出现；
- 哪些国家、平台、产品形态和路线更容易进入 `READY_FOR_BENCH`；
- 证据完整度是否影响开发选择；
- App、游戏、跨平台迁移、热点方向的转化率；
- 从选品到开发、RC、上架、30/90 天结果的真实漏斗；
- 哪些方法版本带来更好的结果。

这些指标必须带业务定义、时间范围、数据新鲜度和证据状态。直接把原始表拖进 BI 工具，容易产生跨路线混排、把 WATCH 当 SELECTED、把排期当上线等错误。

## 看板分层

### 组合总览

- 总候选、证据包、深度研究、路线入选、资料包、开发中、QA、RC、已提交、已上架；
- App / 游戏 / 跨平台迁移 / 日常热点的数量与转化；
- A/B/C 路线分别展示，不做跨路线总分；
- 数据更新时间、证据完整度、阻塞数量。

### 市场与机会

- 国家 × 平台 × 产品形态矩阵；
- 品类增长、持续性、评论痛点和竞争密度；
- 源平台 → 目标平台迁移机会；
- 热点信号时间线、持续性和过期状态。

### 研究质量

- 来源覆盖、新鲜度、冲突和 `insufficient_data`；
- 每条路线的研究→入选转化；
- 候选→资料包→排期转化；
- 证据缺口导致的退回、阻塞和淘汰。

### 开发与经营

- 项目状态泳道；
- 一周版本完成率、延期和阻塞原因；
- RC 率、发布率、商店审核周期；
- D1/D7/D30、下载、收入、留存和停止原因；
- 方法版本与真实经营结果对照。

## 统一指标层

建议先建立 `metric_definitions`，每个指标包含：

- `metric_id`；
- 中文名称与定义；
- 维度与过滤条件；
- 时间窗口；
- 数据来源；
- 新鲜度要求；
- 是否允许估算；
- 权限级别；
- 对应 API/MCP 工具。

示例指标：

- `opportunity_count`：按状态统计的机会数量；
- `evidence_completeness_rate`：证据完整度达标的候选比例；
- `route_selection_rate`：同一路线候选进入 `ROUTE_SELECTED` 的比例；
- `bench_ready_rate`：入选项目进入 `READY_FOR_BENCH` 的比例；
- `weekly_rc_rate`：每周形成 RC 的项目数；
- `release_verified_rate`：有真实发布验证回执的项目比例；
- `d30_survival_rate`：发布后 D30 仍满足最低指标的项目比例。

## Agent/MCP 接入

指标层成熟后，提供只读工具：

```text
get_portfolio_overview
compare_opportunity_modes
compare_routes
get_migration_matrix
get_research_quality
get_development_funnel
get_release_verified_status
explain_metric
```

Agent 必须拿到指标定义、查询时间、过滤条件、来源和缺口，不能只返回一个无来源的数字。

## 实施顺序

1. 在现有网站内新增 `/dashboard` 和 `/dashboard/methodology`；
2. 加入 ECharts，先用 D1 聚合 API；
3. 建立指标定义和快照表，固定口径；
4. 加入项目、开发、发布、经营回流事件；
5. 数据量和查询压力达到阈值后迁移 ClickHouse；
6. 再接 Cube Core 或 Lightdash，为 Web 和 Agent 提供统一语义层；
7. Superset 作为内部探索工具，PostHog 作为产品行为分析工具。

## 采用门槛

- 看板数字能回链到候选、报告、运行和证据；
- 所有指标有时间范围和数据新鲜度；
- 不混合路线排名；
- `READY_FOR_BENCH`、`BUILDING`、`RELEASED` 只能由对应回执驱动；
- Agent 查询结果带来源、过滤条件和 `insufficient_data`；
- 看板不会把估算、排期或草稿显示成真实上线结果。
