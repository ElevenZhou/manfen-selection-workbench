# 统一网站、总控边界与资料包说明

> 结论：网站只建设一次；选品 Loop 每次只生成并保存一份新报告。选品总控做到 `READY_FOR_BENCH`，开发由独立开发台消费资料包。

## 1. 单一长期网站

统一网站位于 `site/`，正式地址为 <https://select.1add2.com>，由 ChatGPT / Codex Sites 托管并使用 D1 保存历史报告。

当前访问模式为 `public`：同事、朋友和上下游协作方无需登录 ChatGPT，拿到链接即可浏览。公开访问不等于允许写入；报告入库、飞书推送和未来管理操作仍必须在服务端校验并保护密钥。

每次周运行、即时运行或指定方向运行，不再生成一套新网站，而是：

```text
研究运行
  → 三路线各自完成评选
  → 为路线入选项生成资料包
  → Publisher 生成 website-report JSON
  → POST /api/reports
  → D1 新增不可覆盖的报告版本
  → 同一网站按发布时间进入报告时间线
```

相同 `report.id` 拒绝覆盖。报告修订必须使用新的版本 ID，以便保留原结论、修订原因和方法版本。

当前网站栏目：

- 驾驶舱：最新一期摘要、三路线结果、资料包和排期概览；
- 选品报告：按时间倒序查看全部历史报告；
- 选品总表：跨报告筛选全部候选，支持产品形态、路线、决策、资料包状态、品类、市场和关键词；
- 报告详情：市场脉搏、来源、三路线各自排名、机会判断、1–3 个改进点和资料包状态；
- 资料包：说明开发台拿到什么、什么时候可以开工；
- 开发排期：只安排产能，不反向改变路线评选；
- 报告入库：人工粘贴 JSON 或由 Publisher 调用 API 保存。

报告提交契约见 `schemas/website-report.schema.json`。网站只负责展示和存档，不能重算路线分数、混排三条路线或修改选品结论。

公开站点只允许展示经过清理的内容。Webhook、Token、Cookie、供应商密钥、付费数据原件、未授权用户材料和本机绝对路径不得进入报告、资料包下载物、前端代码或浏览器响应。

## 2. 选品总控做到哪里

`app-selection-loop` 负责：

1. 读取目标、范围和上次运行；
2. 现用现取证据和趋势信号；
3. 分别运行 Engine A、B、C；
4. 每条路线独立建池、评分、排名和最终评选；
5. 为每个 `ROUTE_SELECTED` 生成完整工作台资料包；
6. 把本次报告保存到统一网站；
7. 根据开发台容量生成独立排期；
8. 完成 Schema、证据、链接、数量、路线隔离和非覆盖 QA。

它不直接实现 App。原因不是能力不足，而是生命周期和验收对象不同：选品 Loop 对“为什么值得做、做什么”负责；开发 Loop 对“实现是否正确、能否交付”负责。两者通过稳定资料包连接，可以独立重跑、独立扩容和独立追责。

推荐层级：

```text
App Factory Loop（未来可选）
  ├─ App Selection Loop
  │    └─ 输出 READY_FOR_BENCH 资料包
  └─ 多个 App Build Loop / 独立开发台
       └─ 输出构建、测试、RC 和发布候选
```

## 3. 一个完整资料包有什么

每个入选项目一个独立目录：

```text
outputs/workbench-packages/<package_id>/
├── manifest.json
├── 00-package-index.md
├── 01-product-brief.md
├── 02-evidence-and-references.md
├── 03-brand-ui-direction.md
├── 04-build-master-prompt.md
├── 05-acceptance-criteria.md
├── 06-growth-plan.md
└── 07-analytics-and-stop.md
```

内容分为八组：

1. **索引与来源**：包版本、候选 ID、路线、路线内排名、产品形态、真实目标平台、方法版本、来源 run、证据路径、状态和完整度。
2. **产品说明**：目标用户、触发场景、核心任务、当前替代方案、失败结果、产品承诺、最小成功结果、范围和非目标。
3. **证据与参考**：竞品、替代方案、workaround、领先信号或实验；每项标注真实对象类型、官方商店或证据链接，并说明用户为何使用、学习什么、重构什么、禁止复制什么。
4. **少而精的改进**：仅 1–3 项；每项包含用户证据、当前失败、修改方案、预期结果、验证指标和明确不做的部分。
5. **品牌与 UI**：主名、备选名、定位、性格、语气、图标方向；唯一主视觉方向、颜色令牌、字体、组件、核心页面、全部状态、无障碍和适配。
6. **开发主提示词**：目标、必读顺序、固定范围、技术栈、仓库、推荐 Skills、实施阶段、数据与异常、测试、截图、构建证据、自主边界和暂停条件。
7. **三视角验收**：用户视角、项目经理视角、推广视角分别有可检查的通过条件，不使用“看起来不错”式主观表述。
8. **增长、埋点与停止**：定位、关键词、素材角度、商店素材、渠道、冷启动测试；关键事件、成功指标、预算边界、复评点和停止条件。

完整结构由 `schemas/workbench-package.schema.json` 约束。只有状态为 `READY_FOR_BENCH` 的包可以进入开发台；缺证据、范围冲突或验收不完整的包必须停在 `DRAFT / REVIEW / BLOCKED`。

产品形态、参考对象类型、标签和链接规则统一遵循 `docs/14-产品形态与参考对象分类规范.md`。

## 4. 开发台拿到包后的第一步

开发台不能重新选品，也不能擅自扩大范围。它先：

1. 按 `00-package-index.md` 的顺序读取全部文件；
2. 校验 `manifest.json` 和资料包状态；
3. 冻结 1–3 个核心改进点、非目标和三视角验收；
4. 输出实现计划和风险；
5. 再进入设计、开发、测试和 RC。

如果真实开发发现核心假设错误，资料包退回为 `RETURNED`，由选品系统修订并产生新版本，不在开发台里悄悄改变产品方向。
