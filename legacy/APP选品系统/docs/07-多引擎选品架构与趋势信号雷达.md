# 多引擎选品架构与趋势信号雷达

> 版本：v1.0  
> 阶段：Architecture / Research-only  
> 目标：把竞品微创新、市场缺口、第一性原理和新需求挖掘组织成三个可独立调用、独立评选、可审计和可扩展的 App 机会系统。

## 1. 设计原则

1. 三条路线起点不同，证据、评分、排名和最终评选也必须独立。
2. 热点、Star、搜索和流量是领先信号，不是需求真值。
3. 没有直接竞品不等于没有现实参考；新需求必须用替代方案、workaround、行为或实验补足证据。
4. 所有候选都必须回答：谁、在什么场景、要完成什么、现在怎么做、为什么不够、我们改善什么结果。
5. 每个 App 只保留 1–3 个关键改变。
6. 任何引擎都不能绕过所属路线的排序、证据门槛和停止条件。
7. 实际发布结果必须反向校准信号、评分和引擎命中率。

## 2. Loop 组织的能力架构

```text
Input Gateway
  → 自然语言、URL、文件、API、供应商导出和历史run

Auto Loop Control Plane
  → 建立合同、路由、依赖检查、重试、QA、汇总和交付

Independent Core Skills
  → 数据证据、信号雷达、路线A、路线B、路线C
  → 资料包、网站发布、开发排期和结果校准

Shared Contracts & Evidence Ledger
  → Task、Result、Signal、Evidence、Candidate、Package

Output & Feedback
  → 报告、网站、15个资料包、独立排期和经营结果回流
```

Loop 不包含路线业务判断。三条路线 Skill 各自拥有评分、门槛和最终5个；其他 Skill 也必须可以脱离 Loop 独立使用。完整组件和双模式调用协议见 `docs/10-Loop与独立技能架构.md`。

## 3. 趋势信号雷达

### 3.1 信号域

| 信号域 | 典型数据 | 主要意义 | 常见误判 |
|---|---|---|---|
| 热点讨论 | 提及量、独立作者、跨平台、问题意图 | 新问题和人群变化 | 新闻围观、争议、机器人 |
| GitHub / 开源 | Star快照、Fork、Contributor、Release、下载 | 技术供给成熟、开发者采用 | Star炒作、不代表C端需求 |
| 搜索趋势 | 7/30/90天增长、相关查询、国家扩散 | 主动需求和认知增长 | 新闻词、季节性、品牌事件 |
| Web / App流量 | 访问、下载、MAU、来源和留存 | 产品采用和渠道变化 | 付费买量、一次性活动 |
| 商店市场 | 排名、下载、收入、评论、更新 | 已验证产品需求 | 榜单短期波动 |
| 技术变化 | API、模型、硬件、成本、能力边界 | 新方案成为可能 | 技术演示没有用户任务 |
| 人口与生活阶段 | 年龄、教育、就业、租房、育儿、照护 | 结构性新需求 | 宏观趋势无法触达 |
| 政策与平台 | 法规、商店、支付、隐私、工作规则 | 强制任务和市场重构 | 窗口太小、合规成本过高 |

### 3.3 信号评分

信号评分只决定研究优先级，不决定开发：

| 维度 | 分数 |
|---|---:|
| 增长速度 | 20 |
| 增长加速度 | 15 |
| 持续性 | 15 |
| 跨来源确认 | 20 |
| 问题/产品意图 | 15 |
| 受影响人群广度 | 10 |
| 数据质量 | 5 |

初始晋级规则：

```text
RAW：单个来源首次异常
WATCH：连续多个采集周期
CONFIRMED：至少两类独立来源一致，或一个强行为来源持续
ROUTED：能够解释受影响用户、任务和变化原因
```

阈值必须在 Data Spike 和 Pilot 中校准，不把初始分数当作已验证标准。

### 3.4 采集节奏

- 热点和事件：每小时或每 4 小时；
- GitHub、搜索和流量异常：每日；
- 商店、排名和评论：每日或按供应商配额；
- 使用、留存和收入：每周；
- 人口、政策和结构变化：每月加事件触发；
- 信号去重、聚类和路由：每日；
- 命中率校准：每月。

## 4. 三条发现引擎

### 4.1 Engine A：竞品验证与微创新

起点：

- 已经增长或长期稳定的 App；
- 明确竞品；
- 被验证的游戏玩法；
- 商店、流量、评论或收入变化。

原生门槛：

- 至少 3 个直接竞品；
- 下载、活跃/留存、收入和评论交叉判断；
- 至少一个跨竞品痛点；
- 只提出 1–3 个改进点。

输出重点：学习什么、为什么有效、改进什么、不可复制什么。

### 4.2 Engine B：市场缺口与第一性原理重构

起点：

- 用户用多个工具拼接工作流；
- 人工服务、表格、聊天软件或线下流程；
- 市场需求大但满意度低；
- 某国家、语言、年龄、职业或无障碍人群被忽略；
- 新技术已经能显著降低步骤、成本或错误。

流程：

```text
定义用户任务和期望结果
  → 列出现有替代方案
  → 定位共同失败结果
  → 拆除历史产品假设
  → 从结果重新设计流程
  → 选择最小切入口
  → 访谈、人工服务、原型或落地页验证
```

原生评分：

| 维度 | 分数 |
|---|---:|
| 任务和痛点强度 | 20 |
| 现有供给缺口 | 20 |
| Workaround与付出证据 | 15 |
| 结果改善幅度 | 15 |
| 付费或迁移意愿 | 10 |
| 用户可触达性 | 10 |
| 实现可行性 | 5 |
| 工厂复用 | 5 |

原生门槛：

- 至少 3 个替代方案或真实 workaround；
- 至少 3 类独立需求证据；
- 一个可测量的结果改善；
- 一次低成本前置验证；
- 不把“市场上没有”当作市场缺口证明。

### 4.3 Engine C：新需求与趋势机会

起点：

- 热门事件和社会变化；
- 新模型、API、硬件或技术成本下降；
- 年轻人进入新生活阶段；
- 工作、教育、家庭、消费和内容行为改变；
- 搜索、讨论、GitHub和流量同步增长；
- 政策、隐私、支付或平台规则变化。

流程：

```text
识别外部变化
  → 解释谁的行为被改变
  → 提出新增任务、风险或焦虑
  → 找到当前临时解决方式
  → 判断需求寿命和扩散速度
  → 设计窗口期内可上线的最小产品
  → 用搜索、行为、访谈、等待名单或付费测试验证
```

原生评分：

| 维度 | 分数 |
|---|---:|
| 外部触发强度 | 15 |
| 受影响人群 | 15 |
| 行为变化程度 | 15 |
| 领先信号加速度 | 15 |
| 持续性 | 15 |
| 供给缺口 | 10 |
| 上线窗口匹配 | 5 |
| 付费/使用意图 | 5 |
| 工厂复用 | 5 |

原生门槛：

- 一个有时间和来源的真实变化；
- 至少 3 个独立领先信号；
- 明确人群、任务和当前临时方案；
- 明确 `Flash / Emerging / Structural` 生命周期；
- 至少一次行为或实验验证；
- 能在窗口关闭前交付。

生命周期：

- `Flash`：少于 8 周，优先网页、活动工具或快速实验；
- `Emerging`：约 2–12 个月，可做小型 App 和快速迭代；
- `Structural`：一年以上，适合长期 App 和产品家族。

## 5. 路线独立评审

每条路线只回答“这是不是本路线中的好机会”，不得用一个混合总分比较不同路线。

- Engine A 使用竞品验证评分：需求、增长、长期使用、商业化、跨竞品痛点、参考质量、AI/工厂复用和获客；
- Engine B 使用 4.2 的市场缺口评分；
- Engine C 使用 4.3 的新需求趋势评分；
- 各路线默认晋级分数为 75，可在 Pilot 中分别校准；
- 同一个 `80分` 在不同路线中含义不同，不得用于跨路线排序。

进入所属路线候选池：

- 所属路线评分不低于该路线门槛；
- 数据完整度不低于 80%；
- 通过所属引擎原生门槛；
- 至少两类独立证据；
- 有目标用户、核心任务、触发场景和当前替代方案；
- 有 1–3 个结果型改进；
- 有下一次验证和停止指标。

## 6. 状态机

```text
RAW_SIGNAL
  → WATCH_SIGNAL
  → CONFIRMED_SIGNAL
  → ROUTED_HYPOTHESIS
  → EVIDENCE_BUILDING
  → ROUTE_QUALIFIED
  → ROUTE_POOL
  → ROUTE_SELECTED / ROUTE_BACKUP / ROUTE_WATCH / REJECTED
  → READY_FOR_BENCH
  → BUILDING
  → QA
  → RC
  → SUBMITTED
  → RELEASED
  → SCALE / ITERATE / MAINTAIN / KILL
```

每次状态变化必须记录：

- 时间；
- 执行人或自动任务；
- 原因；
- 使用的证据版本；
- 分数变化；
- 下一状态条件。

## 8. 网站与驾驶舱

新增页面：

- `/signals`：信号流、异常、国家、来源和状态；
- `/signals/[id]`：原始值、基线、增速、证据和路由；
- `/engines`：三引擎漏斗、命中率和经营结果；
- `/scouting/[run]`：单次研究；
- `/candidates/[id]`：所属路线评分、路线内排名和证据；
- `/methodology`：规则版本和阈值变更。

关键经营指标：

- 每千条原始信号产生多少确认信号；
- 每个引擎产生多少合格候选；
- 合格候选进入所属路线最终 5 个的比例；
- RC率、发布率、30/90天存活率；
- 每个引擎的下载、留存、收入和停止率；
- 数据成本、研究时长、开发时长和单个成功App成本。

## 9. 路线产量与开发排期

默认每条路线独立评选 5 个，合计 15 个。每条路线都可以扩大研究池，也可以通过调用参数调整最终数量；若合格项目不足，必须如实少产出。

当前五开发台是独立的下游产能，不承担选品裁决。排期可根据战略、窗口期、复用条件和团队能力从 15 个资料包中领取项目；没有被领取的入选项目保留在所属路线待开发队列。

## 10. 落地阶段

### Stage A：两周信号 Data Spike

目标：验证能否稳定获得并规范化真实信号。

接入或手工导出：

- 一个热点讨论源；
- GitHub公共指标每日快照；
- Google Trends页面/导出；
- 一个Web流量源；
- 一个App市场源。

退出证据：

- 500条以上真实信号样本；
- 字段完整率；
- 重复率；
- 每源成本和限制；
- 20个确认信号；
- 10个可路由假设；
- Go / No-Go。

### Stage B：四周三引擎 Prototype

每个引擎至少完成 10 次研究，验证：

- 原生门槛能淘汰弱机会；
- 三引擎输出可以进入同一 Schema；
- 每条路线的评分能在路线内部稳定排序；
- 不生成跨路线总分或混合榜单；
- 人工复核时间可接受。

### Stage C：十二周 Pilot

- 每周让三条路线分别评选，并由独立排期装载开发台；
- 保留所有被拒原因；
- 跟踪 RC、发布、30/90天表现；
- 每月校准信号阈值和评分；
- 不根据一两个成功案例修改整体规则。

### Stage D：Production

只有 Pilot 证明信号、研究、开发和经营闭环有效后，才建设：

- 自动采集和队列；
- 供应商正式配额；
- 监控、重试、去重和审计；
- 数据版本与模型版本；
- 多操作者权限；
- 成本和回滚控制。

## 12. 研究数量与路线决策

默认一次完整三路线运行：

| 路线 | 候选池 | 最终入选 | 路线备选 | 路线观察 |
|---|---:|---:|---:|---:|
| Engine A：竞品验证 | 20 | 5 | 3 | 12 |
| Engine B：缺口重构 | 20 | 5 | 3 | 12 |
| Engine C：新需求 | 20 | 5 | 3 | 12 |
| 合计 | 60 | 15 | 9 | 36 |

每条路线的候选池可以更大；表中数量是默认报告口径，不是采集上限。

路线决策：

- 每条路线 5 个 `ROUTE_SELECTED`：各自生成完整工作台资料包；
- 每条路线 3 个 `ROUTE_BACKUP`：保存证据，等待同路线补位或复评；
- 每条路线 12 个 `ROUTE_WATCH`：保存证据和下一次验证；
- 未通过门槛的候选单独归档；
- 三条路线互不挤占名额，不做分数换算或混合淘汰。

单独调用某条引擎时使用：

```yaml
candidate_pool_count: 20
final_selection_count: 5
backup_count: 3
```

可以改为任意合理数量。数量是研究目标而不是证据豁免。

## 13. 开发工作台交接

选品系统与开发台保持独立。开发台不需要重新理解整个选品项目，只接收一个自包含的 Workbench Package。

每个 `ROUTE_SELECTED` 资料包包含：

```text
manifest.json
00-package-index.md
01-product-brief.md
02-evidence-and-references.md
03-brand-ui-direction.md
04-build-master-prompt.md
05-acceptance-criteria.md
06-growth-plan.md
07-analytics-and-stop.md
```

核心改变必须少而精：

- 最少1个、最多3个；
- 每个改变必须对应用户证据；
- 每个改变必须说明改善的结果；
- 不允许用大量次要功能掩盖核心差异。

品牌与UI必须重新设计：

- 一个主品牌方向和一个备选名称；
- 独立定位、语气和图标方向；
- 颜色令牌、字体、间距和核心组件；
- 核心页面和状态；
- 明确竞品中可以学习与禁止复制的部分。

验收分三个视角：

1. 用户：任务是否完成、首次价值是否清晰、错误是否可恢复、体验是否可信；
2. 项目经理：范围、流程、测试、埋点、质量、进度和停止条件；
3. 推广：定位、商店页、关键词、素材、归因、激活和付费路径。

完整规范见 `docs/09-开发工作台交接资料包规范.md`。
