# 随时选品侦察技能使用与接入规范

> 技能：`$app-opportunity-scout`  
> 作用：在固定周选品之外，随时发起一次可追溯的宽泛或定向选品研究  
> 边界：发现机会并形成证据包，不直接批准开发台；候选只进入所属路线并参加路线内评选

> 多引擎定位：当前技能主要承担 Engine A“竞品验证与微创新”。市场缺口与第一性原理、新需求与趋势机会由独立发现引擎执行；三条路线使用共同基础字段，但各自评分、排名和评选。

> 调用定位：技能既可接受自然语言独立运行，也可接受 Auto Loop 的标准任务信封。两种入口使用同一证据门槛和输出契约，详见 `docs/10-Loop与独立技能架构.md`。

### 1.1 选品与竞品必须 1-1 对应

每个候选必须先确定一个 `primary_competitor`，作为该选品唯一的主对应竞品。候选的产品方向、核心任务、拆解和改进方案都围绕这个主对应竞品展开。其他产品可以继续提供参考，但必须进入独立的 `reference_objects` 字段，并说明是玩法、增长、商业化、分发或替代方案参考。

输出时禁止把同一组竞品数组复制给多个候选。主对应竞品缺失、重复或不匹配时，候选停在 `REVIEW/BLOCKED`；不能把它标记为 `SELECTED` 或生成 `READY_FOR_BENCH` 资料包。

## 1. 为什么需要独立技能

每周报告适合稳定生产，但市场机会并不只在周一出现。操作者可能随时看到：

- 某个 App 或品类突然增长；
- 一个明确国家或人群需求；
- 一个值得参考的竞品；
- 跨竞品反复出现的用户痛点；
- 新技术带来的核心任务优化；
- 一个值得验证的游戏玩法。

选品侦察技能把这些临时信号变成标准研究任务。所有运行都使用 Engine A 的证据和评分规则，结果可进入 Engine A 路线池，但不会与 Engine B、Engine C 混合评分。

## 2. 两套入口

| 入口 | 触发方式 | 默认规模 | 最终责任 |
|---|---|---:|---|
| 每周 AutoLoop | 固定周任务 | 每条路线 Top 20、最终 5 个、3 个备选 | 三条路线独立评选、生成资料包、发布周报告 |
| 选品侦察技能 | 随时人工调用或外部自动化触发 | 按模式输出 | 发现 Engine A 机会、建立证据、提出进入该路线候选池建议 |

共同规则：

- 必须有具体竞品；
- 必须记录数据来源、市场、平台、周期和采集日期；
- 必须区分官方、第三方估算、实际观察、内部数据和假设；
- 每个产品只保留 1–3 个关键改进点；
- 数据缺失不得补造；
- 游戏的市场表现不能代替可玩性测试。

## 3. 六种模式

### broad：宽泛扫描

覆盖多个国家、商店、品类和商业模式。默认输出 20 个排名机会和 5 个深度分析。

```text
使用 $app-opportunity-scout 宽泛扫描当前 App 市场，
输出 20 个机会、5 个深度方案，并标记数据缺口。
```

### directed：指定方向

可以组合国家、商店、品类、人群、需求、技术或商业模式。默认输出 10 个机会和 3 个深度分析。

```text
使用 $app-opportunity-scout 研究日本市场、面向老年人的工具类 App，
重点寻找高频刚需、订阅投诉和可以减少操作步骤的机会。
```

### competitor-expand：竞品扩展

从一个或多个具体 App 出发，寻找直接竞品、相邻产品、替代方案和用户未满足需求。

```text
使用 $app-opportunity-scout 围绕 Forest 展开研究，
不要只找专注计时器，也分析任务、习惯、数字健康和游戏化替代品。
```

### pain-mine：用户痛点

从用户任务或困难出发，先证明用户正在寻找或使用解决方案，再形成产品机会。

```text
使用 $app-opportunity-scout 挖掘
“家长很难管理孩子每天的屏幕时间和任务奖励”相关产品机会。
```

### gameplay-hunt：游戏玩法

寻找已经被市场验证的机制、核心循环、主题和人群组合。默认输出 10 个机会和 3 个灰盒测试方案。

```text
使用 $app-opportunity-scout 研究轻量合成游戏，
寻找增长稳定但评论中反复出现节奏、广告或体力痛点的玩法。
```

这里的 `SELECTED` 只表示进入灰盒验证，不表示玩法已经被证明好玩。

### refresh：旧候选复评

重新采集最新版本、排名、下载、活跃、收入、评论和竞品变化，输出：

- `promote`
- `hold`
- `demote`
- `reject`

必须解释新旧分数和决策变化。

## 4. 运行输入

最小输入可以只有一句自然语言。信息不完整但可研究时，技能自行采用默认值并记录假设。

也可以传入符合 `schemas/skill-task.schema.json` 的任务信封。独立调用时由技能生成 `task_id` 和 `run_id`；Loop 调用时保留 `parent_run_id`，最终都返回 `schemas/skill-result.schema.json` 对应的结果。

每条引擎默认目标为5个通过门槛的候选，也可以显式输入：

```yaml
qualified_count: 8
```

如果达到证据门槛的候选不足，实际输出可以少于目标数量。

推荐结构：

```yaml
mode: directed
direction: japan-senior-tools
countries:
  - JP
stores:
  - Apple App Store
  - Google Play
categories:
  - Utilities
target_users:
  - 60+ smartphone users
must_include:
  - named competitor if any
exclude:
  - medical diagnosis
ranked_count: 10
deep_dive_count: 3
data_cutoff: latest
```

只有以下情况需要暂停询问：

- 需要购买付费数据；
- 需要登录尚未授权的账户；
- 目标范围互相冲突；
- 需要公开发布、发送或部署；
- 需要改变正在运行的开发台。

## 5. 研究流程

```text
解析请求和默认范围
  → 创建不可覆盖的 run_id
  → 建立足够宽的发现池
  → 匹配直接、相邻和替代竞品
  → 采集市场、使用、收入、评论、关键词和版本证据
  → 识别用户价值、痛点和请求
  → 实际体验核心流程
  → 只提出 1–3 个改进点
  → 100 分评分与证据门禁
  → 输出排名、深度方案、淘汰原因和网站数据
```

浏览、排名、评论、价格和版本会变化，因此每次真实运行都必须重新检查当前来源。

每个候选同时输出 `product_form` 和真实目标平台；每个参考对象输出 `entity_kind`、`url`、`store_url` 与 `store`。真实移动 App / 游戏优先使用官方 Apple App Store 或 Google Play 链接，非 App 对象不得伪造商店链接。字段规则见 `docs/14-产品形态与参考对象分类规范.md`。

## 6. 硬门槛

候选进入 `SELECTED` 至少满足：

- 3 个有链接的直接竞品；
- 数据完整度不低于 80%；
- 总分不低于 75；
- 至少两类独立来源支持需求或使用；
- 有跨竞品重复出现的用户价值和用户痛点；
- 每个数字包含市场、平台、周期、采集日期、来源和数据类型；
- 只有 1–3 个核心改进点；
- 可以描述为一个清晰人群、一个核心任务、一个差异。

技能内状态含义：

| 状态 | 含义 |
|---|---|
| SELECTED | 有资格进入下一期 Engine A 路线候选池 |
| BACKUP | 证据通过，但相对优先级较低 |
| WATCH | 有信号，但关键证据不足或过期 |
| REJECTED | 需求、差异化、可行性或证据完整性不通过 |

## 7. 输出目录

每次运行创建独立目录，不覆盖历史：

```text
outputs/scouting/YYYY-MM-DD-方向/
├── run.json
├── report.md
├── signals.json
├── candidates.json
├── candidates.csv
├── evidence.json
├── evidence.csv
├── review-themes.csv
└── website.json
```

文件责任：

- `run.json`：原始请求、模式、范围、假设、时间和数据源；
- `report.md`：结论、排名、深度方案、淘汰原因和下一步验证；
- `signals.json`：触发本次研究的标准化趋势信号；
- `candidates.json`：符合统一 Schema 的候选对象；
- `candidates.csv`：候选评分和决策；
- `evidence.json`：符合证据 Schema 的逐条依据；
- `evidence.csv`：逐条竞品指标或观察；
- `review-themes.csv`：用户价值、痛点和请求主题；
- `website.json`：允许网站展示的结构化摘要。

## 8. 进入 Engine A 路线池

即时侦察结果不能直接装载开发台。

进入流程：

1. 技能完成证据和评分；
2. 通过硬门槛的候选标记为 `scouting_selected`；
3. 下一次周任务读取对应运行目录；
4. 检查数据新鲜度、链接和冲突；
5. 只与当周 Engine A 候选重新评分和排序；
6. 路线决策输出 `route_selected` 或其他状态；
7. `route_selected` 生成完整工作台资料包；
8. 独立开发排期从资料包队列领取项目，不改变路线排名。

必须保留：

- 原始 `run_id`；
- 候选 ID；
- 被引用的证据行；
- 技能建议与周决策的差异；
- 进入、拒绝或延后的原因。

## 9. 网站更新

网站新增：

- `/scouting`：所有即时侦察运行；
- `/scouting/[run]`：单次研究详情；
- 候选页的“来源运行”和“周决策状态”；
- 周报告的“本周引用即时研究”。

网站必须明确区分：

```text
即时推荐
  → Engine A 路线候选
  → 路线最终入选
  → 待开发
  → 开发中
  → RC
  → 已发布
```

技能默认只准备本地 `website.json`。公开部署或发布仍需单独授权。

## 10. 自动化边界

技能可以：

- 被自然语言随时调用；
- 被其他流程调用；
- 被定时任务触发；
- 被异常增长或新竞品信号触发。

技能不会自行建立定时任务。真正的无人触发运行需要独立自动化，并明确：

- 频率；
- 研究范围；
- 数据预算和配额；
- 失败重试；
- 通知方式；
- 是否允许更新网站；
- 是否允许写入所属路线候选池。

无论由谁触发，都不能绕过 Engine A 的证据和路线决策门槛。

## 10.1 与趋势信号雷达的关系

技能可以消费趋势信号，但不能把单个热点直接升级为候选：

```text
RAW_SIGNAL
  → WATCH
  → CONFIRMED_SIGNAL
  → 路由到发现引擎
  → ENGINE_QUALIFIED
  → ROUTE_POOL
  → ROUTE_SELECTED / ROUTE_BACKUP / ROUTE_WATCH
```

如果信号指向已有快速增长 App，路由到本技能；如果指向未被满足的任务或人工流程，路由到缺口重构引擎；如果源于新技术、事件或人群行为变化，路由到新需求引擎。
