# 产品形态与参考对象分类规范

> 版本：v1.0  
> 生效日期：2026-07-25  
> 适用范围：候选、路线报告、选品总表、证据、资料包、开发排期、飞书卡片和后续经营数据

## 1. 为什么要分类

“App 选品”是系统名称，不代表每个机会最终都必须做成手机 App。研究对象可能是移动 App、手机游戏、网页产品、桌面软件、开源项目、系统功能、开发平台、技术标准或研究报告。

分类必须解决四个问题：

1. 操作者一眼看懂候选最终准备做成什么；
2. 不把网页、PC 软件或技术标准误当成手机 App；
3. 开发资料包的目标平台与产品形态一致；
4. 参考对象的商店链接和证据链接各司其职。

## 2. 入选项目的 `productForm`

每个候选必须且只能声明一个主产品形态：

| 值 | 中文标签 | 典型交付面 | 默认目标平台 |
|---|---|---|---|
| `mobile_app` | 移动 App | 工具、知识、生活服务 | iOS、Android |
| `mobile_game` | 手机游戏 | 休闲、益智、超休闲游戏 | iOS、Android |
| `web_app` | Web 应用 | 浏览器内完成主要任务 | Web |
| `desktop_app` | 桌面 App | 本地桌面软件、重度生产力工具 | macOS、Windows |
| `cross_platform` | 跨端应用 | 同一核心任务横跨 Web、桌面和移动端 | 按资料包明确列出 |

`productForm` 描述准备开发的产品，不描述参考对象。若一个方向未来可以扩展到多个端，仍应以第一版主要任务所在的端作为主形态；只有第一版就必须跨端闭环时才使用 `cross_platform`。

## 3. 参考对象的 `kind`

每个竞品、相似品、替代方案或证据来源必须声明实际类型：

除对象类型外，候选还必须区分关系：每个候选只有一个 `primary_competitor`（主对应竞品，1-1），可有多个 `reference_objects`（其他参考对象）。`primary_competitor` 负责回答“我们准备对应哪个产品做我们的版本”；`reference_objects` 只负责补充玩法、增长、商业化、分发或替代路径。两类字段不得合并，也不得用全局对象列表覆盖所有候选。

| 值 | 中文标签 | 说明 |
|---|---|---|
| `mobile_app` | 移动 App | 官方商店存在的非游戏移动应用 |
| `mobile_game` | 手机游戏 | 官方商店存在的移动游戏 |
| `web_product` | Web 产品 | 主要通过浏览器使用的网站或在线产品 |
| `desktop_app` | 桌面软件 | 主要在 macOS、Windows 或 Linux 使用的软件 |
| `open_source_project` | 开源项目 | 以代码仓库和开源发行物为主要载体 |
| `system_feature` | 系统功能 | 操作系统内置能力，不是独立 App |
| `developer_platform` | 开发平台 | API、SDK、模型平台或开发者服务 |
| `technical_standard` | 技术标准 | 协议、规范、联盟标准或技术定义 |
| `research_report` | 研究报告 | 调查、行业报告、论文或研究文章 |

`kind` 与 `relation` 不冲突：`kind` 回答“它是什么”，`relation` 回答“它与候选是什么关系”。

## 4. 链接规则

每个参考对象保留两套不同职责的地址：

- `url`：官网、产品页、文档、GitHub、技术标准、研究报告或本次证据来源；
- `storeUrl`：真实移动 App 或手机游戏的官方 Apple App Store / Google Play 详情页。

同时保存：

- `store = apple_app_store | google_play | null`；
- 非独立移动 App 的 `storeUrl` 必须为 `null`；
- 不得用第三方客户端、同名产品或非官方商店页替代；
- 页面点击真实 App 或游戏时优先进入 `storeUrl`，其他对象进入 `url`。

当参考对象是 Android App 或手机游戏时，可额外保存 `apkDownloads`（最多 3 个）作为下载入口。每项包含 `provider`、`label`、`url` 和 `status`；只有在联网核对页面与产品匹配后才写 `verified`，否则写 `needs_verification`。下载源按以下顺序优先：APKMirror、Uptodown、F-Droid、Amazon Appstore、Aurora Store，其次才使用 Aptoide 或 APKPure。所有 APK 链接必须是 HTTPS 详情页，不能凭包名猜测或拼接 URL；官方商店链接仍保留在 `storeUrl`，两者职责不同。

## 5. 网站展示与筛选

统一网站执行以下规则：

- 产品名附近显示 `productForm` 中文标签；
- 参考对象名称附近显示 `kind` 中文标签；
- “选品总表”顶部提供“产品形态”筛选；
- 分类标签只帮助识别和筛选，不参与三条路线评分；
- 标签使用紧凑、可读、可访问的文字章，不只依赖颜色；
- 手机端不得因为标签增加而产生横向溢出。

## 6. 资料包、开发排期与飞书

资料包必须包含：

- `objective.product_form`；
- 与产品形态一致的 `target_platforms`；
- 每个参考对象的 `kind`、`store`、`store_url` 和证据 `url`。

开发排期显示产品形态，但不能根据形态改变路线排名。飞书卡片在入选项目名称旁显示产品形态，在参考对象名称旁显示对象类型；真实 App 或游戏的名称链接仍指向官方商店。

## 7. 机器字段映射

| 产物 | 项目形态字段 | 参考对象类型字段 |
|---|---|---|
| 路线候选 JSON | `product_form` | 通过 Evidence 关联 |
| Evidence JSON/CSV | 候选关联 | `entity_kind` |
| Website report JSON | `productForm` | `references[].kind` |
| Workbench package | `objective.product_form` | `references[].kind` |
| D1 candidates | `product_form` | `reference_apps` JSON 内的 `kind` |

snake_case 用于研究、路线和资料包产物；camelCase 用于网站报告与 TypeScript 模型。

## 8. 完整性与 QA

以下任一情况不得标记完整：

- 候选缺少 `product_form / productForm`；
- 参考对象缺少 `entity_kind / kind`；
- Web 或桌面项目仍无理由地默认 `iOS + Android`；
- 移动 App 或游戏存在官方商店页但没有保存 `storeUrl`；
- 非 App 对象被错误链接到同名商店产品；
- 网站、资料包和飞书使用了互相矛盾的分类。

分类是可修订事实。若后续调研证明形态判断错误，应创建报告或资料包新版本并保留修订记录，不覆盖历史结论。
