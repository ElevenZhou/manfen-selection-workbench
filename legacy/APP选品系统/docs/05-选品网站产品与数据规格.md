# 选品网站产品与数据规格

> 版本：v1.3  
> 实现：`site/` 是唯一长期网站，使用 D1 保存报告；每次运行只新增报告，不重复建站。  
> 线上地址：<https://select.1add2.com>，公开访问，无需登录 ChatGPT。  
> 目标：让操作者访问一个网站，就能按时间看到每周或即时清单、数据依据、案例、分析、改进点、资料包和开发排期。

## 1. 用户与使用场景

第一阶段包含两类用户：

- 操作者：查看完整选品结论、资料包、开发排期和发布入口；
- 协作阅读者：同事、朋友及上下游伙伴，通过公开链接查看报告、依据、参考案例和改进方向。

核心任务：

- 看本周市场发生了什么；
- 分别查看三条路线本周各自选出的 5 个 App；
- 查看每个选择的竞品和数据依据；
- 审批、替换或停止候选；
- 看五个开发台的状态；
- 看已发布 App 的真实结果是否支持选品方法。

## 2. 导航

当前已实现的最小闭环导航为 `/`、`/reports`、`/reports/[id]`、`/candidates`、`/packages`、`/schedule`、`/ingest` 和 `/api/reports`。其中“选品总表”支持按报告期、路线、决策、资料包状态、产品形态、品类、市场和关键词筛选。下表其余页面是随着证据粒度和经营数据接入逐步扩展的目标信息架构，不应通过每次运行重复建站来实现。

| 页面 | 路径 | 工作 |
|---|---|---|
| 驾驶舱 | `/` | 三路线入选结果、开发台状态、异常 |
| 周报告 | `/weekly/[week]` | 每周完整清单和结论 |
| 趋势信号 | `/signals` | 热点、GitHub、搜索、流量和市场异常 |
| 信号详情 | `/signals/[id]` | 原始值、基线、增速、持续性、来源和路由 |
| 发现引擎 | `/engines` | 三引擎的漏斗、命中率、候选和经营结果 |
| 即时侦察 | `/scouting` | 所有宽泛、定向、竞品、痛点和玩法研究 |
| 侦察详情 | `/scouting/[run]` | 单次研究的范围、证据、排名和接入状态 |
| 候选库 | `/candidates` | 全量筛选和排序 |
| 候选详情 | `/candidates/[id]` | 数据、竞品、评论、产品方案 |
| 竞品详情 | `/competitors/[id]` | 单个竞品的趋势和功能 |
| 开发队列 | `/build-queue` | 15 个入选项目的待排期、开发、QA、RC |
| 资料包 | `/workbench-packages` | 三条路线入选项目的开发台交接资料和完整性 |
| 资料包详情 | `/workbench-packages/[id]` | 产品、品牌、UI、提示词、验收和增长方案 |
| 开发台 | `/benches/[id]` | 单台任务、风险和证据 |
| 已发布 | `/released` | 下载、留存、收入、版本和停止 |
| 数据源 | `/sources` | 覆盖、更新时间、成本、异常 |
| 方法 | `/methodology` | 评分、门槛和版本 |

## 3. 驾驶舱

顶部 KPI：

- 本周扫描记录数；
- 候选簇；
- 证据包；
- 深度分析；
- Engine A / B / C 各自的入选和备选数量；
- 五台 RC 产能；
- 本周实际 RC；
- 数据新鲜度；
- 红灯数量。

主区域：

1. Engine A 最终 5 个及路线备选；
2. Engine B 最终 5 个及路线备选；
3. Engine C 最终 5 个及路线备选；
4. 五开发台状态和待开发队列；
5. 增长最快品类和国家；
6. 上周产品结果；
7. 数据异常和缺口。

## 4. 候选卡

列表卡只显示决策需要的信息：

- 工作名；
- 统一尺寸产品图标；优先使用可追溯的产品图标，也可使用竞品图标或系统生成图标；
- 产品形态标签、品类、国家、真实目标平台；
- 状态；
- 所属路线评分和路线内排名；
- 数据完整度；
- 直接竞品数量；
- 3/6/12 月下载、MAU、收入变化；
- 核心需求；
- 一个主要痛点；
- 1–3 个改进点；
- 至少 1 个可点击的竞品、相似品或替代方案名称，并显示参考对象类型；真实移动 App / 游戏使用官方商店链接，其他对象使用官方页或证据来源；
- 推荐开发台。

点击进入详情，不在卡片堆大量文字。

## 5. 候选详情页

### 决策头部

- ROUTE_SELECTED / ROUTE_BACKUP / ROUTE_WATCH / REJECTED / READY_FOR_BENCH / BUILDING / RC / RELEASED；
- 所属路线评分、路线内排名、置信度、数据完整度；
- 推荐开发台；
- 决策人、决策时间、方法版本；
- 继续、返工、替换和停止按钮。

### 数据证据

- 下载趋势；
- DAU/WAU/MAU；
- Stickiness；
- D1/D7/D30；
- Session 和使用时长；
- 收入、RPD、ARPDAU；
- 评分、评论量；
- 关键词和广告；
- 每个图表都显示数据源、国家、时间和采集日期。

### 竞品对比

- Engine A：至少 3 个直接竞品和相邻产品；
- Engine B：至少 3 个替代方案、人工流程或 workaround；
- Engine C：至少 3 个独立领先信号，以及相邻产品或临时解决方式；
- 功能矩阵；
- 定价和商业化；
- 更新时间线；
- 用户认可价值；
- 高频痛点；
- 可学习与不可复制资产。

### 产品方案

- 目标用户；
- 触发场景；
- 核心任务；
- 已验证需求；
- 1–3 个改进点；
- AI 作用；
- 核心流程；
- 第一版范围；
- 商业化；
- 埋点；
- 验收和停止条件。
- 品牌主方向和备选方向；
- UI视觉方向、颜色令牌和核心页面；
- 开发工作台资料包状态和路径；
- 用户、项目经理、推广三个视角的验收状态。

## 6. 周报告页

固定模块：

1. 本周摘要；
2. 数据范围和缺口；
3. 市场脉搏；
4. 增长榜；
5. 耐用榜；
6. 痛点榜；
7. Engine A：Top 20、最终 5 个、3 个备选、12 个观察；
8. Engine B：Top 20、最终 5 个、3 个备选、12 个观察；
9. Engine C：Top 20、最终 5 个、3 个备选、12 个观察；
10. 各路线淘汰原因；
11. 15 个入选项目的资料包状态；
12. 独立开发排期；
13. 上周结果反馈；
14. 各路线方法变化。

网站不得生成跨路线总分或混合排行榜。路线筛选和排名必须始终带 `source_engine`，开发排期可以跨路线查看，但不能改写路线评选结果。

## 6.1 即时侦察页

即时侦察与周报告分开显示，避免把“研究建议”误认为“已经批准开发”。

列表页显示：

- `run_id`、运行日期和模式；
- 宽泛或指定方向；
- 研究范围和数据截止时间；
- 发现、排名和深度分析数量；
- SELECTED / BACKUP / WATCH / REJECTED 数量；
- 数据完整度和最新鲜来源；
- 是否已进入某一期所属路线候选池；
- 是否被路线决策采用。

详情页显示：

- 原始研究请求和系统假设；
- 数据源清单和缺失数据；
- 排名清单；
- 候选、竞品、评论主题和改进策略；
- 即时决策与路线决策的差异；
- “加入下一期所属路线候选池”“保持观察”“归档”操作；
- 引用该运行的周报告。

状态必须分层：

```text
scouting_selected
  ≠ route_selected
  ≠ ready_for_bench
  ≠ building
  ≠ released
```

## 7. 数据实体

候选以 `product_form` 表示交付形态，参考证据以 `entity_kind` 表示真实对象类型；`store_url` 只对真实移动 App / 游戏成立。完整枚举、标签和链接规则统一见 `docs/14-产品形态与参考对象分类规范.md`。

最小实体：

```text
app
publisher
store_listing
signal_event
signal_cluster
signal_route
market_metric
usage_metric
rank_metric
keyword_metric
ad_creative
review
review_theme
competitor_group
scouting_run
scouting_candidate
candidate
candidate_score
evidence_pack
product_brief
improvement_strategy
weekly_report
selection_decision
build_bench
build_run
qa_result
release
released_metric
data_source
methodology_version
```

`candidate.source_engine` 必须是：

```text
competitor_validated
gap_redesign
emerging_demand
```

`reference_evidence.reference_type` 可以是：

```text
direct_competitor
adjacent_product
substitute
workaround
leading_signal
pilot_result
internal_result
```

关系：

```text
scouting_run
  → scouting_candidate
  → candidate
  → selection_decision
  → build_run
```

`scouting_candidate` 只有通过证据门槛并被加入所属路线候选池后，才创建或关联正式 `candidate`。

## 8. 关键字段

所有指标表必须包含：

- `app_id`
- `store`
- `country`
- `metric_name`
- `metric_value`
- `metric_unit`
- `period_start`
- `period_end`
- `collected_at`
- `source`
- `source_url`
- `value_type`: official / estimate / internal
- `confidence`

没有这些字段，网站不能把数字显示为可用于决策的证据。

所有趋势信号还必须包含：

- `signal_role`: demand / technology / competitor / event / demographic；
- `baseline_value`；
- `growth_rate`；
- `acceleration`；
- `persistence_days`；
- `problem_intent`；
- `product_intent`；
- `paid_bias`；
- `routed_engine`。

## 9. 网站更新格式

每周输出：

```text
content/
└── 2026-W31/
    ├── weekly-report.md
    ├── summary.json
    ├── engine-a/
    │   ├── candidates.json
    │   ├── decisions.json
    │   └── evidence-packs.json
    ├── engine-b/
    │   ├── candidates.json
    │   ├── decisions.json
    │   └── evidence-packs.json
    ├── engine-c/
    │   ├── candidates.json
    │   ├── decisions.json
    │   └── evidence-packs.json
    ├── workbench-packages.json
    ├── development-schedule.json
    └── sources.json
```

第一阶段网站从这些文件静态生成。三个引擎目录不得合并为可排序总榜；`development-schedule.json` 只表示开工顺序。数据结构稳定后，再切换数据库。

即时侦察输出：

```text
outputs/
└── scouting/
    └── 2026-07-29-japan-senior-tools/
        ├── run.json
        ├── report.md
        ├── candidates.csv
        ├── evidence.csv
        ├── review-themes.csv
        └── website.json
```

网站读取 `website.json` 生成即时侦察页面。进入所属路线候选池时只保存引用、候选 ID 和最新证据，不覆盖原始运行目录。

## 10. 技术路线

### Prototype

- Markdown + JSON；
- 静态网站；
- Git 版本管理；
- 手工审批后更新；
- 不接真实付费 API。

### MVP

- vinext / React；
- Sites 托管与 D1；
- 报告入库 API；
- 公开只读浏览；
- 候选审批；
- 五开发台状态；
- 周报告自动生成。

### Pilot

- 真实供应商 API；
- 评论聚类；
- 评分服务；
- 开发台任务接口；
- QA 和 RC 回传；
- 已发布 App 经营数据回流。

### Production

- 多操作者和权限；
- 供应商配额与成本；
- 任务队列与重试；
- 监控、备份和恢复；
- 决策审计；
- 数据版本；
- 供应商异常降级；
- 多开发台扩容。

## 11. 网站验收

Prototype 通过标准：

- 可以按周访问报告；
- 可以看到三条路线各自的 Top 20、最终5个、3个备选和依据；
- 每个候选可以进入详情；
- 所有关键数字有来源和日期；
- 可以看到五台状态；
- 页面可以按产品形态、品类、国家、状态和分数筛选；
- 可以查看所有即时侦察运行及其是否被路线决策采用；
- 可以区分即时推荐、路线入选、待开发、开发中和已发布；
- 可以从路线候选追溯到原始 `run_id` 和证据；
- 手机和桌面都能使用；
- 无数据时明确显示缺失，不显示 0；
- 方法版本可追溯。

## 12. 当前实现边界与后续入口

统一网站、D1 报告入库、选品总表、资料包视图、开发排期、产品形态筛选和飞书推送入口已经实现并公开部署。固定网址采用 `public` 访问模式，匿名访问应返回正常页面，不得要求协作方登录 ChatGPT。当前仍未自动获得或接入：

- 付费数据服务及其 API 凭证；
- 持续采集服务；现阶段继续使用联网大模型现用现查；
- 真实开发台的构建、测试和商店发布状态；
- 发布后的下载、激活、留存、收入与停止原因反馈。

这些能力在获得相应授权、凭证或真实经营数据后按独立阶段接入，不阻塞现有选品与资料包闭环。
