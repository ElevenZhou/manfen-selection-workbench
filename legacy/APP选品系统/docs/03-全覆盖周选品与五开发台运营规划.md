# 全覆盖周选品与五开发台运营规划

> 版本：v1.0  
> 日期：2026-07-25  
> 当前阶段：Stage 1，三路线、统一网站、资料包、分类字段与飞书发布闭环已落地；继续扩充数据源与经营反馈  
> 目标：形成“全市场扫描 → 每周选品 → 五开发台并行 → 网站发布 → 经营反馈”的持续系统

## 1. 目标与基本判断

长期目标是实际生产、发行和运营 1000+ App，而不是只产生 1000 个想法。

系统的核心不是让 AI 随机想产品，而是：

1. 尽可能完整地获取各商店 App 数据；
2. 找到已经被真实用户验证、长期稳定或快速增长的竞品；
3. 用活跃、留存、收入、评论和实际体验判断需求；
4. 每个候选提炼 1–3 个明确改进点；
5. 形成标准化产品说明；
6. 交给五个 AI 开发台并行实现；
7. 把开发、测试、上架和经营结果反馈给选品模型。

商店审核完成时间不可控，所以“开发台每周输出一个”定义为：

> 每台每周交付一个通过内部 QA、具备商店提交条件的 Release Candidate。商店审核通过另行跟踪。

## 2. 规模与产能模型

### 2.1 稳定期周产能

默认配置：

| 项目 | 数值 |
|---|---:|
| 操作者 | 1 人 |
| 每人管理开发台 | 5 个 |
| 每台每周 Release Candidate | 1 个 |
| 每周理论产能 | 5 个 |
| 每年有效生产周 | 46 周 |
| 每年理论产能 | 230 个 |

按照这个模型：

- 单人、五开发台完成 1000 个 Release Candidate，理论需要约 4.35 年；
- 若目标为一年 1000 个，需要约 22 个开发台；
- 按每人管理 5 个台计算，需要约 5 名操作者。

这些数字是产能假设，不是已验证事实。前 12 周 Pilot 的任务之一，就是测出实际吞吐量、返工率和上架通过率。

### 2.2 周选品数量

选品数量不由当前 5 个开发台倒推。三条路线各自负责自己的候选池和最终结果。

默认每条路线每周决策：

- 可扫描和研究任意数量；
- 建立 `Top 20` 路线候选池；
- 独立评选 `5 个最终入选`；
- 保留 `3 个路线备选`；
- 保留 `12 个路线观察候选`；
- 其余淘汰或归档，并记录原因。

因此，一次完整周运行默认输出 3 份互不混排的 Top 20，共 15 个最终入选、9 个备选和 36 个观察。数量可由调用参数调整；证据不足时不得为了凑数降低门槛。

### 2.3 周漏斗

稳定期建议漏斗：

```text
本周新增、更新或异常增长 App：50,000–200,000
  → 机器初筛：1,000
  → 自动竞品聚类：200
  → Competitor Evidence Pack：50
  → 深度分析：20
  → 各路线独立候选池
  → 每条路线最终入选：5
  → 每条路线备选：3
```

“50,000–200,000”指自动处理记录量，不是人工逐个阅读。实际规模由数据供应商配额和成本决定。

开发排期是下游独立流程：当前五开发台每周最多领取 5 个项目，其余已入选项目留在所属路线的待开发队列，不回退、不跨路线重排。

## 3. 每周运行节奏

### 周一：全量扫描与异常发现

自动任务：

- 拉取新上架、更新、榜单和品类数据；
- 更新 3、6、12、24 个月下载和收入趋势；
- 更新 DAU、WAU、MAU、Stickiness、Session、时长和留存；
- 识别增长拐点、榜单跃迁、收入异常和更新后变化；
- 将同类 App 自动聚类。

产物：

- 全量增量数据；
- 机器初筛 1,000；
- 异常增长与长期稳定榜。

### 周二：竞品证据与用户需求

自动任务：

- Engine A 为候选匹配至少 3 个直接竞品和 3–10 个相邻产品；
- Engine B 匹配至少 3 个替代方案、人工流程或工具拼接 workaround；
- Engine C 聚合至少 3 个独立领先信号，并寻找相邻产品、临时方案或实验依据；
- 抓取最近 90 天、12 个月评论；
- 聚类“用户价值、痛点、价格、广告、订阅、功能请求、Bug”；
- 读取版本更新时间线、截图、功能、定价和广告素材；
- 生成 50 份 Competitor Evidence Pack。

人工任务：

- 快速检查竞品匹配是否正确；
- 删除错误品类、错误国家和不可比较对象。

### 周三：深度体验与选品会

AI 深度分析 20 个候选：

- 实际安装和体验直接竞品；
- 记录首开、核心任务、付费点、广告、留存循环；
- 区分产品价值、内容资产、品牌资产和可优化流程；
- 每个候选只提出 1–3 个高价值优化点；
- 判断 AI 应该出现在前台、后台还是完全不需要。

每条路线分别做四个决定：

- `ROUTE_SELECTED`：该路线最终 5 个；
- `ROUTE_BACKUP`：该路线 3 个备选；
- `ROUTE_WATCH`：该路线 12 个观察；
- `REJECTED`：其余归档并记录原因。

### 周四：产品说明与开发台装载

为三条路线共 15 个最终入选输出完整资料包，为路线备选保留证据和简版说明：

- 竞品证据包；
- 一页产品说明；
- 产品需求文档；
- 核心流程；
- 1–3 个改进策略；
- AI 结合点；
- 商业化方案；
- 设计参考与不可复制资产；
- MVP / Release Candidate 范围；
- 验收标准；
- 数据埋点和停止条件。

开发排期从 15 个完整资料包中按产能领取项目。当前五个开发台每周最多领取 5 个，其余项目留在所属路线待开发队列。

### 周五：网站发布与下周准备

网站发布：

- 本周市场脉搏；
- 三条路线各自的 Top 20；
- 每条路线最终 5 个、3 个备选和 12 个观察；
- 每个候选的依据、竞品、数据、痛点和改进点；
- 五开发台状态；
- 上周产品的开发、QA、上架和经营反馈。

同时冻结下一周输入数据的时间边界，避免同一周报告反复变化。

## 4. 五个 AI 开发台

### 4.1 建议分工

| 开发台 | 默认方向 | 原因 |
|---|---|---|
| Bench 1 | 工具 | 复用 OCR、文件、相机、订阅等能力 |
| Bench 2 | 知识/学习 | 复用内容结构、RAG、测验和进度系统 |
| Bench 3 | 轻量游戏 | 复用关卡、广告、IAP、埋点和远程配置 |
| Bench 4 | 生活方式/生产力 | 复用账户、提醒、收藏和习惯循环 |
| Bench 5 | 最高分机会台 | 不限品类，用于突发增长和备选替换 |

分工是效率工具，不是选品限制。Bench 5 保持灵活，其他台也可以在某周切换品类。

### 4.2 单台周循环

```text
周四：装载已批准的产品包
周五：架构、依赖、风险和验收测试冻结
周一：核心闭环可运行
周二：功能完成和自动测试
周三：视觉、错误状态、埋点和商业化
周四：设备测试、QA、问题修复
周五：Release Candidate、商店素材草案和交接
```

流水线需要错峰。第 1 周装载产品，第 2 周开始形成稳定周输出。

### 4.3 一个人如何管理五个台

操作者不负责逐行编程，主要负责：

- 审批产品边界；
- 处理 AI 无法决定的产品取舍；
- 查看每台每日红灯；
- 审批敏感权限、付费和外部服务；
- 验收核心用户流程；
- 决定通过、返工、替换或停止。

每台开发台必须提供统一状态：

| 状态 | 含义 |
|---|---|
| GREEN | 按范围推进，无阻塞 |
| YELLOW | 有风险但仍可能本周完成 |
| RED | 需要替换、降范围或人工决策 |
| READY_QA | 已进入验收 |
| RC | 已形成 Release Candidate |
| STOPPED | 已停止并记录原因 |

建议操作者每天只做两次集中检查：上午 30 分钟、下午 45 分钟。开发台必须异步留下证据，不依赖操作者持续盯屏。

## 5. 数据从哪里获得

### 5.1 全市场与多商店基础层

推荐 `42matters` 或 `Appfigures API` 作为主数据入口。

- Appfigures API 可按 App、国家、日期和商店提供 iOS / Google Play 下载及收入估算：
  https://docs.appfigures.com/api/reference/v2/estimates
- 42matters 提供 API 和 File Dump，并覆盖 Google Play、Apple、Amazon、Tencent、Huawei 等多个商店：
  https://42matters.com/our-app-and-sdk-intelligence

用途：

- 建立 App 主表；
- 发现新 App 和版本更新；
- 下载、收入、排名、评分和评论；
- 开发者、SDK、权限和商店元数据；
- 多商店统一 ID。

### 5.2 真实使用与留存层

推荐 `Similarweb App Intelligence`；预算充足时用 `Sensor Tower`。

Similarweb 官方列出的指标包括 DAU、WAU、MAU、Session、Daily Stickiness、D1/D7/D30 留存、下载、收入、评论和用户画像，并提供 37 个月历史、58 个国家覆盖：
https://www.similarweb.com/corp/apps/

Sensor Tower 提供下载、收入、使用时长、Session、留存、关键词、评论、更新与获客来源分析：
https://sensortower.com/blog/product-spotlight-app-performance-insights

用途：

- 排除“下载高但没人持续使用”；
- 识别长期使用和高粘性产品；
- 比较增长来自新增用户还是存量活跃；
- 判断版本更新是否带来实际使用变化。

### 5.3 游戏层

推荐 `AppMagic` 作为游戏下载、收入、子品类、玩法、IAP 和 LiveOps 研究工具，活跃与留存仍用 Similarweb 或 Sensor Tower 补充。

用途：

- 发现长生命周期玩法；
- 区分超休闲和混合休闲；
- 研究玩法标签、关卡循环、IAP 和活动；
- 识别下载稳定但收入上升的游戏。

### 5.4 搜索需求、广告和获客层

推荐：

- AppTweak：下载、收入、排行榜、发行商组合和 ASO；
  https://www.apptweak.com/en/aso-blog/app-download-revenue-estimates
- MobileAction：关键词、下载趋势、评论分析、广告素材和投放网络；
  https://www.mobileaction.co/pricing/

用途：

- 判断用户在搜索什么；
- 发现增长关键词；
- 看竞品是否依赖大量广告；
- 研究能持续投放的创意角度；
- 区分产品自然增长和短期买量。

### 5.5 评论和真实体验层

任何平台评论分析都不能替代实际阅读和体验。

每个 Engine A 最终入选项目至少需要：

- 3 个直接竞品；
- 每个竞品 200–500 条评论；
- 最近 90 天和最近 12 个月两个窗口；
- 至少一半样本来自 1–3 星，或按真实星级分布加权；
- 记录原始评论、国家、版本、日期和来源 URL；
- 人工体验至少 2 个头部竞品和 1 个新增长竞品。

Engine B 和 Engine C 不强制伪造直接竞品，分别执行 `docs/07` 中的替代方案门槛和领先信号门槛。

## 6. 基于什么分析

### 6.1 Engine A 原生评分：100 分

| 维度 | 权重 | 主要证据 |
|---|---:|---|
| 已验证需求 | 20 | 下载、MAU、评论量、搜索量 |
| 增长质量 | 15 | 3/6/12 个月下载、MAU、收入 |
| 长期耐用 | 10 | 24–37 个月稳定性、更新持续性 |
| 使用与留存 | 10 | Stickiness、D1/D7/D30、Session、时长 |
| 商业化 | 10 | 收入、RPD、ARPDAU、订阅/IAP |
| 痛点机会 | 15 | 跨竞品高频痛点、强情绪、未解决需求 |
| 竞品参考质量 | 10 | 直接竞品数量、数据完整度、可学习机制 |
| AI / 工厂复用 | 5 | AI 是否改善核心任务、共享模块利用率 |
| 获客可解释性 | 5 | 关键词、素材、渠道、自然/付费结构 |

Engine A 进入深度分析的默认门槛：

- 总分 ≥ 75；
- 数据完整度 ≥ 80%；
- 至少 3 个直接竞品；
- 每个关键数字有来源、地区、时间范围和采集日期；
- 至少一个被多个竞品评论重复验证的用户痛点；
- 至少一个能在 1–3 周做出闭环的改进点。

这些门槛需要在 Pilot 中用真实结果校准。

Engine B、Engine C 的独立评分方法见 `docs/07-多引擎选品架构与趋势信号雷达.md`。三条路线的分数只在路线内部使用，不互相比较。

### 6.2 耐用型 App

重点看：

- 24–37 个月 MAU 和下载没有持续性衰退；
- D30、使用时长或 Session 稳定；
- 收入和更新仍在持续；
- 评论中核心价值长期不变；
- 产品不是只依赖一次性事件。

### 6.3 快速增长 App

重点看：

- 3、6、12 个月增长同时成立；
- MAU 与下载同步，而不是只增加安装；
- 收入或使用时长至少一个同步增长；
- 增长不是单一国家、单一广告活动或短期热点；
- 更新、素材或功能变化能够解释增长。

## 7. 如何确认用户真的需要

不能只依赖“有人下载”。

至少需要四类证据：

1. **行为证据**：MAU、留存、Session、使用时长；
2. **付费证据**：收入、订阅、IAP、RPD；
3. **表达证据**：评论中反复出现的价值和痛点；
4. **替代证据**：用户愿意使用多个竞品、手工流程或付费替代方案。

强需求的典型组合：

```text
稳定或增长的 MAU
  + 可接受的留存
  + 用户反复描述同一个价值
  + 用户为结果付费或容忍广告
  + 多个竞品共同存在
```

## 8. 如何确认游戏玩法好玩

竞品数据可以证明“这种玩法有人玩”，但不能证明我们的版本好玩。必须增加可玩测试。

### Gate G1：竞品玩法已验证

- 至少 3 个直接玩法竞品；
- 下载、MAU、留存或收入至少两个指标长期成立；
- 评论中“好玩、上瘾、放松、挑战”等正面主题稳定；
- 玩法不是完全依赖 IP、美术或巨额买量。

### Gate G2：48 小时灰盒测试

- 同一核心想法做 3 个最简变体；
- 至少 30 名目标玩家；
- 记录教程完成率、首局完成率、主动再开一局和主观乐趣评分；
- 只保留最强一个变体。

建议初始阈值：

- 教程完成率 ≥ 70%；
- 主动再开一局 ≥ 40%；
- 首局完成率 60%–85%；
- 主观乐趣平均 ≥ 4/5。

### Gate G3：7 天封闭测试

- 100–300 名测试用户；
- 记录 D1、D3、D7、Session/DAU、平均时长和关卡流失；
- 与同子品类基准比较，而不是使用一个全游戏统一标准。

没有真实可玩数据的游戏，只能进入原型队列，不能进入批量发行队列。

## 9. 每周必须输出什么

### 9.1 周选品报告

- 市场脉搏；
- 本周数据范围和来源；
- 增长榜、耐用榜、痛点榜；
- Engine A：Top 20、最终 5 个、3 个备选、12 个观察；
- Engine B：Top 20、最终 5 个、3 个备选、12 个观察；
- Engine C：Top 20、最终 5 个、3 个备选、12 个观察；
- 15 个入选项目的工作台资料包和独立开发排期；
- 上周选品结果反馈；
- 数据缺口和争议。

### 9.2 每个候选的 Competitor Evidence Pack

- 候选基本信息；
- 3 个直接竞品和 3–10 个相邻产品；
- 下载、收入、活跃、留存、评分、评论；
- 3/6/12/24 月趋势；
- 核心流程、功能、定价、广告和更新；
- 评论价值主题和痛点主题；
- 数据来源和采集日期。

### 9.3 产品说明

- 用户是谁；
- 什么时候产生需求；
- 当前使用什么；
- 为什么竞品已验证；
- 我们只优化哪 1–3 点；
- AI 放在哪里；
- 第一版做什么、不做什么；
- 如何赚钱；
- 验收指标和停止条件。

### 9.4 改进策略

必须逐项对应竞品证据：

| 竞品事实 | 用户问题 | 我们的改进 | 验证指标 |
|---|---|---|---|
| 某流程平均 6 步 | 评论反复抱怨复杂 | 缩短为 2 步 | 任务完成率、完成时间 |

禁止只写“体验更好”“加入 AI”“界面更美”这类无法验证的表达。

## 10. 网站规划

### 10.1 网站的工作

网站不是宣传页，而是选品和生产驾驶舱。

首页应该回答：

- 本周扫描了多少 App；
- 哪些品类和国家在增长；
- 三条路线各自的 Top 20；
- 三条路线各自的最终 5 个和备选；
- 五开发台现在在做什么；
- 上周产品的结果如何。

### 10.2 页面结构

```text
/
├── /weekly/[week]              每周选品报告
├── /candidates                全候选库
├── /candidates/[id]           候选详情与证据
├── /competitors/[id]          竞品详情
├── /build-queue               开发队列
├── /benches/[1-5]             五开发台状态
├── /released                  已发布产品与经营数据
├── /sources                   数据源、更新时间和覆盖
└── /methodology               评分、门槛和版本记录
```

### 10.3 候选详情页

必须显示：

- 产品形态和与之匹配的真实目标平台；
- 当前状态：路线入选、路线备选、路线观察、淘汰、待开发、开发中、已发布；
- 所属路线评分、路线内排名和各维度分数；
- 数据完整度和置信度；
- 直接竞品对比；
- 下载、MAU、收入、留存趋势；
- 评论主题和原始证据；
- 可学习机制；
- 1–3 个改进点；
- 产品说明；
- 数据来源、地区、时间和最后更新时间。

每个参考对象必须显示实际类型。真实移动 App / 游戏名称链接官方商店，Web、桌面、开源、平台、标准和报告链接官网或证据来源；详细字段遵循 `docs/14-产品形态与参考对象分类规范.md`。

### 10.4 更新机制

Stage 1 建议先用 `Markdown/JSON + 静态网站`：

- 每周报告和候选数据保存在 Git；
- 自动生成网站；
- 每次更新有版本和差异；
- 无需第一天建设复杂后台。

Stage 2 数据量增长后改为：

- Postgres 数据库；
- 数据采集任务；
- 评分服务；
- 评论聚类服务；
- 网站读取 API；
- 登录、权限和审核记录。

### 10.5 网站发布节奏

- 周一更新市场扫描状态；
- 周三发布 Top 20 草案；
- 周五发布三条路线各自的最终5个、3个备选和产品说明；
- 每日更新开发台状态；
- 发布后按日/周回填下载、留存、收入和问题。

## 11. 分阶段实施

### Stage 0：规划与模板

本次交付：

- 运营规划；
- AutoLoop 主提示词；
- Excel 工作簿；
- 网站规格；
- README 更新。

### Stage 1：两周数据 Spike

目标：

- 选择并试用数据供应商；
- 拉取真实 App 样本；
- 验证国家、品类、历史深度、API 和导出；
- 比较同一 App 在两个平台的趋势一致性。

通过标准：

- 至少 5 个国家、5 个品类、500 个 App；
- 至少一个真实使用数据源；
- 至少一个游戏下载与收入数据源；
- 至少一个多商店 API；
- 输出 Go/No-Go 与成本。

### Stage 2：四周选品 MVP

目标：

- 每周自动生成三条路线各自的 Top 20；
- 人工分别批准三条路线各自的最终5个和3个备选；
- 网站显示报告和候选详情；
- 不接开发台生产。

通过标准：

- 连续 4 周稳定运行；
- 每个路线最终入选项目有完整证据包；
- 重复研究率低；
- 人工每周审核时间 ≤ 6 小时。

### Stage 3：十二周 Pilot

目标：

- 接入五开发台；
- 每周装载 5 个；
- 测量实际 RC 产量、返工、QA 和上架通过。

通过标准：

- 连续 8 周平均每周 ≥ 4 个 RC；
- 关键流程通过率 ≥ 95%；
- 严重缺陷为 0；
- 返工率、成本和操作者时间可接受；
- 至少一批产品获得真实用户数据。

### Stage 4：生产扩容

只有 Pilot 通过后，才增加操作者和开发台。

重点建设：

- 数据供应商正式合同；
- API 配额、监控和成本控制；
- 共享开发组件；
- 自动测试和设备矩阵；
- 商店发布与版本管理；
- 经营数据回流；
- 权限、备份、恢复和审计。

## 12. 角色与责任

即使只有一个人，也要把角色分开：

| 角色 | 责任 |
|---|---|
| 数据研究 | 数据覆盖、趋势、异常、来源 |
| 用户研究 | 评论、需求、痛点、替代方案 |
| 产品负责人 | 竞品学习、改进点、产品说明 |
| 游戏评测 | 玩法、灰盒、留存和乐趣 |
| 开发台 | 实现、测试、修复和交付 |
| QA/发布 | 验收、设备、素材、上架准备 |
| 经营复盘 | 下载、留存、收入和停止决策 |

AI 可以承担多个角色，但同一个结论必须经过数据、产品和 QA 三个视角检查。

## 13. 当前需要的下一阶段输入

要开始真实数据 Spike，需要：

- 数据预算范围；
- 首批关注国家；
- 是否购买 Similarweb / Sensor Tower；
- 是否购买 AppMagic；
- 是否使用 Appfigures API 或 42matters；
- 五开发台实际技术栈、目标平台和设备条件；
- 网站是否仅内部访问。

这些输入不影响本次规划完成，但会决定下一阶段供应商和系统架构。

## 14. 随时选品侦察与周生产线的关系

除了固定每周运行，还需要允许操作者在任意时间发起一次独立选品侦察，例如：

- 宽泛寻找当前增长机会；
- 指定国家、商店、品类、人群或商业模式；
- 围绕某个竞品扩展直接、相邻和替代产品；
- 从一个用户痛点反向寻找已存在的需求；
- 挖掘轻量游戏玩法和主题组合；
- 重新评估以前的候选。

即时侦察由 `$app-opportunity-scout` 执行。它与 Engine A 周流程共用数据定义、100 分评分、竞品门槛和证据完整度，但不直接占用开发台。

标准数据流：

```text
即时问题或市场信号
  → 独立 Scouting Run
  → 竞品、指标、评论和产品体验证据
  → 形成 SELECTED / BACKUP / WATCH / REJECTED 建议
  → 通过硬门槛的候选写入下一期 Engine A Route Pool
  → 只与当周 Engine A 候选重新评分和排序
  → 路线最终入选后生成完整资料包
  → 独立开发排期领取项目
```

必须保持三个边界：

1. 技能中的 `SELECTED` 表示“具备进入 Engine A 路线候选池的资格”，不等于已经排期开发；
2. 临时发现的机会不能插队挤占正在运行的开发台，除非开发排期明确替换；
3. 即时研究结果必须保存独立 `run_id`、来源和采集日期，周报告引用而不复制成无来源结论。

每次运行输出到：

```text
outputs/scouting/YYYY-MM-DD-方向/
```

网站可以立即展示该次侦察，但必须标记为“即时研究”；只有经过路线决策的候选才显示为“路线入选”或“路线备选”。

详细调用和接入规则见 `docs/06-随时选品侦察技能使用与接入规范.md`。

## 15. 多引擎选品升级

周生产线不再只接收竞品微创新候选，而是接收三条发现引擎的标准化结果：

| 引擎 | 起点 | 原生证据门槛 | 主要风险 |
|---|---|---|---|
| Engine A：竞品验证 | 已有 App、玩法或品类 | 3 个直接竞品 | 同质化、只优化表面 |
| Engine B：缺口重构 | 用户任务、失败结果、人工流程 | 3 个替代方案或 workaround | 需求小、用户不愿迁移 |
| Engine C：新需求 | 事件、技术、搜索、讨论、流量和人群变化 | 3 个独立领先信号，加行为或实验 | 热点短命、把关注误认为需求 |

各路线使用自己的证据门槛、评分模型和路线内排名。Engine A 只评 Engine A，Engine B 只评 Engine B，Engine C 只评 Engine C；不产生跨路线统一分数或总榜。

默认每条路线最终评选 5 个。研究资源可以按当期数据量和战略重点动态调整，但不得因此减少其他路线的最终名额或改变其评分。五开发台从 15 个完整资料包中独立排期，未被领取的项目继续等待，不影响选品结论。

完整架构和状态机见 `docs/07-多引擎选品架构与趋势信号雷达.md`，总控执行提示词见 `docs/08-多引擎选品AutoLoop总控提示词.md`。
