# APP 选品系统 2.0 总控路线图

日期：2026-11-11  
状态：规划已完成，进入 Spike/MVP 排期  
总控：Auto Loop（老大）

## 目标

把现有“研究产物 + 统一报告站点”升级成一个可持续运行的 Web 选品工作台。操作者在一个网站里完成任务创建、研究执行、证据核验、路线评选、资料包生成、排期、结果回流和复盘；App、游戏、跨平台迁移与日常生活/热点使用同一套证据账本和状态机，但保留各自的评分维度。

现有站点已具备 `/`、`/reports`、`/research`、`/candidates`、`/packages`、`/schedule`、`/ingest`、`/selector`、D1/Drizzle、报告入库和飞书幂等推送。目标是增量演进，不重建历史报告，也不把研究建议误标成已立项。

## 四类工作模式

1. **App 机会**：真实竞品、用户任务、评论痛点、商业化和平台覆盖。
2. **游戏机会**：玩法循环、留存/付费、广告素材、关卡或内容生产成本、平台发行风险。
3. **跨平台迁移**：Steam/桌面/主机/Web 的需求迁移到 Android/iOS/Web；增加输入适配、性能、版权/许可、离线能力和轻量化可行性评分。PS、Office 等大型产品只研究“合法的功能重构/兼容工作流”，不复制受保护资产。
4. **日常生活与热点**：事件或趋势信号 → 用户任务 → 可验证的短周期需求；必须记录时间戳、来源、持续性和过期条件。

统一实体增加 `opportunity_mode`、`source_platform`、`target_platform`、`migration_type`、`trend_expiry_at`、`rights_review`、`evidence_freshness`。所有候选继续保留 `source_engine` 与路线内排名，禁止跨路线混排总分。

## 网站工作流

```text
创建任务 → 选择模式/市场/平台/数量/截止时间
  → Agent/MCP 执行研究 → 证据收件箱
  → 人工确认事实/缺口 → 路线评分与评选
  → 生成资料包 → 开发队列/五开发台
  → 结果入库 → 下载、留存、收入、反馈回到方法版本
```

新增页面优先级：

- `/workspace`：任务收件箱、运行状态、失败重试和待处理证据；
- `/signals`、`/signals/[id]`：热点、GitHub、商店、搜索和趋势信号；
- `/migrations`：源平台→目标平台的迁移机会矩阵；
- `/opportunities/[id]`：统一候选详情，显示模式、证据、风险和下一步；
- `/runs/[id]`：Agent/MCP 调用、耗时、来源、缺口、回执与审计；
- `/methodology`：评分版本、门槛、停止条件和变更记录。

现有页面保持 URL 兼容，采用导航分组：发现（总览/信号/研究）、评选（总表/报告/候选）、交付（资料包/排期/结果）、系统（运行/数据源/方法）。移动端使用底部导航或折叠菜单。

## 交付阶段

### Spike（1 周）

- 扩充 schema 与表单：四种模式、源/目标平台、权利审查、过期时间；
- 任务创建保存为 `selection_requests`，状态 `DRAFT → QUEUED → RUNNING → REVIEW → READY_FOR_DECISION → COMPLETED/FAILED`；
- `/workspace` 展示真实运行回执；API 先接本地 runner，Agent/MCP 适配器保留接口；
- 为 App 与游戏各跑一条历史样本回放，验证字段兼容和报告入库。

出口：构建通过；历史报告渲染不变；四模式任务可保存；失败有可读错误和重试入口。

### MVP（2–4 周）

- 证据收件箱与逐条核验；
- 跨平台迁移矩阵与版权/许可门禁；
- 热点信号详情、过期规则和数据新鲜度；
- Agent/MCP 连接器（研究、网页检索、Feishu、文件导入）统一任务信封；
- 候选详情支持“继续研究/退回/加入排期/停止”，所有写入返回业务回执并记录审计。

出口：端到端完成四种模式各一条流程；API 幂等；敏感值不进前端和公开报告；可导出审计记录。

### Pilot（4–8 周）

- 真实团队试用，建立每周运行与复盘；
- 接入授权数据源/导出，记录成本、覆盖率和新鲜度；
- 结果回流到 `released` 与方法版本，建立候选→开发→发布的转化漏斗；
- 运行失败、数据缺口、版权风险、过期热点进入红灯面板。

出口：连续 4 周无阻断性数据或状态错误；关键操作完成率、证据完整率和回流率达标。

### Production

- 服务器部署、域名、TLS、备份、监控、限流、密钥轮换；
- 管理员与公开阅读权限分离；
- 每周发布前自动构建、schema 校验、页面 smoke test 和回滚包；
- 仅在服务器凭据、域名 DNS 权限与发布回执齐备后宣称上线。

## 技术基线

- 前端：现有 Next 16 + React 19 + Vinext/Vite，保留当前视觉系统；
- 数据：Cloudflare D1 + Drizzle；扩展 `selection_requests`、`runs`、`evidence_items`、`signals`、`audit_events`、`platform_migrations`；
- 执行：统一 `skill-task`/`skill-result` 信封，适配 Agent、MCP、API、本地脚本；长任务使用队列与轮询，不在请求线程等待；
- 安全：服务端持有 Feishu/Web/API 密钥；公开站只返回清理后的证据摘要；写入接口需身份、CSRF/幂等键、速率限制和审计；
- 运维：Docker 或 Cloudflare Workers 任选其一，先以当前 Sites/D1 作为 Pilot，生产服务器采用反向代理、TLS、健康检查、备份和回滚。

## 验收门禁

- **事实门**：每个结论都有来源、采集时间、对象类型、缺口；`insufficient_data` 不被填成估算。
- **路线门**：A/B/C 与四种模式分别排名，不生成跨路线总分。
- **迁移门**：源/目标平台、适配工作量、性能、许可/版权、商业化假设齐全。
- **热点门**：信号有时间戳、基线、持续性和过期时间；过期自动降级为 WATCH。
- **状态门**：`scouting_selected ≠ route_selected ≠ ready_for_bench ≠ building ≠ released`。
- **写入门**：每次写入有 HTTP 状态、业务 code、幂等键和可读回执；没有回执保持 pending。
- **发布门**：build、schema、路由 smoke test、移动端可读性、敏感值扫描全部通过。

## 部署与域名清单

当前公开站点为 `https://select.1add2.com`，本轮不直接改 DNS。生产部署需要：服务器 IP/SSH、域名及 DNS 控制权、运行时选择、D1/数据库绑定、密钥注入方式、备份位置和回滚策略。收到这些凭据后执行：

1. 创建 staging，导入脱敏样本；
2. 运行 `npm test`、schema 校验和浏览器 smoke test；
3. 配置环境变量与密钥，不写入仓库；
4. 配置反向代理、TLS、健康检查和日志；
5. 用低流量 canary 验证 `/api/reports`、任务运行、入库和回执；
6. DNS 切换，读回 HTTP 200、业务 code、页面和日志；
7. 生成回滚包与部署记录。

在没有服务器/DNS/密钥回执前，部署状态只能记录为 `READY_FOR_DEPLOYMENT`，不能写成已上线。

## 首批实施顺序

先做 Spike 的任务与运行状态，再做证据收件箱和迁移矩阵，最后做热点信号与结果回流。这样能先验证“网站可操作 + Agent 可见 + 证据可追溯”的核心闭环，再扩展数据源和自动化。
