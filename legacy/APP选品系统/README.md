# APP 选品系统
目标是建立一套能够持续生产、发行和运营 `1000+ App` 的数据化选品与开发系统。

> 安全约定：Webhook、Token、Cookie 和供应商密钥只通过环境变量或密钥系统注入，不写入 README、报告、资料包或网站数据。

经营方向是全覆盖和多数量：持续扫描不同国家、不同商店和全部主要品类，重点关注工具类、知识类和轻量游戏，但不人为把候选限制在少数赛道。系统首先研究用户已经在使用的真实竞品，识别经久耐用、持续增长或近期快速增长的 App；然后基于具体数据、用户评论和实际产品体验，找到可以优化、微创新或结合 AI 的地方。

这里的“多数量”是实际产品组合目标，不只是候选实验数量。我们需要用共享的数据、技术、设计、商业化和发行能力，提高同时研究和开发大量 App 的效率。

核心流程：

```text
全市场、全品类、全商店扫描
  → 发现用户正在使用、长期稳定或快速增长的 App
  → 为每个机会建立真实竞品组
  → 验证下载、活跃、留存、收入和增长质量
  → 分析评论、用户任务、付费原因和未满足需求
  → 实际体验并拆解竞品
  → 提炼少而准的优化点、微创新点和 AI 结合点
  → 批量生成标准化产品方案
  → 分批开发、发行、测量和持续优化
```

当前阶段是 `Stage 1：选品、资料包、统一网站和通知闭环已可运行`。现阶段继续扩大真实数据覆盖，用标准化证据和各路线独立指标持续输出具体选品清单，并把开发与经营结果回流到选品方法。

## 线上网站

- 正式地址：[APP 选品驾驶舱](https://select.1add2.com)
- 托管方式：ChatGPT / Codex Sites 托管，使用平台管理的 D1 保存报告数据。
- 访问方式：`public`。同事、朋友和上下游协作方无需登录 ChatGPT，拿到链接即可浏览。
- 发布原则：线上只展示允许公开的报告、来源摘要和资料包；Webhook、Token、Cookie、供应商密钥、付费数据原件和本机绝对路径不得进入网站。
- 更新原则：网站只建设一次；后续运行向同一网站新增报告和资料包，不为每轮选品重复创建网址。

### 后端与部署边界

Cloudflare / Sites 不只是静态网页托管。本项目当前通过 Cloudflare Worker 运行页面和服务端 API，使用 D1 读写报告、候选和任务状态，并在服务端执行身份校验和飞书推送。现有接口包括 `GET/POST /api/reports`、`POST /api/selection-requests` 和 `POST /api/reports/:id/feishu`。

Cloudflare 适合承载 HTTP API、D1 数据库、R2 文件、Secrets、Cron、Queues 和 Workflows；它不提供常驻 Node 进程，也不适合直接运行本地模型、Docker 服务或长时间 Playwright 浏览器任务。选品任务必须由 Queue/Workflow 异步执行，不能在页面请求中同步等待。

当前 `/api/selection-requests` 已能把请求写入 D1 并返回 `queued`；`scripts/selection-worker.mjs` 可以领取任务，但如果没有配置 `SELECTION_RESEARCH_ADAPTER_URL`，它只能完成领取，不能自行完成研究。执行任务时必须继续检查适配器、运行产物和任务回写；如果适配器缺失，应明确使用项目内的 inline fallback（或保持 `processing/blocked`），不能把“已领取”说成“已执行”。只有报告产物、网站入库和业务回执都读回后，才可标记为完成或已发布。

最近一次已执行任务：`2026-11-13-us-googleplay-puzzle`，任务请求为美国 Google Play Puzzle 榜单、增长较快且评价较好的游戏，输出 3 个候选。产物位于 [`outputs/scouting/2026-11-13-us-googleplay-puzzle/`](outputs/scouting/2026-11-13-us-googleplay-puzzle/)。该次执行采用 inline fallback，已回写任务 `completed`；网站报告入库和飞书推送仍需单独完成并核对回执。

内部使用部署按 [部署规范 V1.0](docs/部署规范V1.0.md) 执行；默认不购买独立 VPS。只有需要常驻 Agent、浏览器集群、本地模型或 Docker 服务时，才单独增加后台执行器，Web 和 D1 仍可继续运行在 Cloudflare。

当前已经上线的两份按需专项调查：

- [抖省省竞品、相邻产品与替代方案调查](https://select.1add2.com/reports/2026-07-26-china-doushengsheng-competitor-map)：发现 10 个机会，深度研究 3 个；当前正式入选 0 个，全部保持 `WATCH`。

专项调查与周期选品共用同一个报告库、选品总表和公开详情页。`WATCH` 项可以展示证据、参考 App、少而精的改进方向和下一步验证要求，但不会生成生产资料包，也不会被写成正式立项。

## 当前总架构

```text
多种输入
  → 自然语言 / URL / 文件 / API / 历史运行
        ↓
Auto Loop 总控
  → 建立任务合同、路由 Skills、检查依赖、验证和汇总
        ↓
独立核心 Skills
  ├─ 数据证据与趋势信号
  ├─ Engine A：竞品验证与微创新 → 独立最终5个
  ├─ Engine B：市场缺口与第一性原理 → 独立最终5个
  ├─ Engine C：新需求与趋势机会 → 独立最终5个
  ├─ 工作台资料包
  ├─ 报告发布到统一网站
  ├─ 飞书互动卡片摘要发布
  └─ 开发排期与结果校准
        ↓
共享事实契约与证据账本
  → 15个资料包 / 统一网站历史报告 / 飞书回执 / 独立开发排期 / 经营反馈
```

Loop 是控制面，不拥有路线评分；Skill 是能力面，既可以被 Loop 调用，也可以接受自然语言、链接、文件或外部系统输入独立运行。两种调用经过同一输入适配、执行同一门禁，并返回同一结果契约。

## 一口气运行

已经安装总控技能 [`app-selection-loop`](/Users/xmm/.codex/skills/app-selection-loop/SKILL.md)。它是完整系统的首选入口，负责连续调度项目内 Skills、外部 Skills、连接器、工具和本地方法，直到得到可验证的最终交付。

```text
使用 $app-selection-loop 一口气完成本周全市场选品：
三条路线各自最终选5个，为入选项目生成完整资料包，
把报告保存到统一网站，输出独立开发排期，并完成QA。
```

也可以只运行其中一段：

```text
使用 $app-selection-loop 只运行市场缺口路线，最终选8个。
使用 $app-selection-loop 从已有ROUTE_SELECTED开始生成全部资料包。
使用 $app-selection-loop 恢复上一次未完成运行，只继续缺失任务。
```

三条引擎不共用同一个“竞品数量”门槛：

- Engine A：至少 3 个直接竞品；
- Engine B：至少 3 个替代方案或真实 workaround；
- Engine C：至少 3 个独立领先信号，加用户行为、替代方案或实验验证。

三条路线的评分含义、证据门槛和排名范围都不同，不做跨路线总分、统一榜单或相互淘汰。开发台产能只决定何时开工，不改变每条路线的选品结果。

### 选品与竞品的对应规则

每个候选必须有一个唯一的 `primary_competitor`，表示“我们这一个选品主要对应、拆解并准备超越的产品”，候选与它保持 1-1 关系。其他可借鉴产品放入 `reference_objects`，并标注它们学习的是玩法、增长、商业化、分发或其他维度。报告、网站、候选详情、资料包和飞书卡片必须把两类对象分开显示；禁止把一组通用竞品数组复制给所有候选。

若主对应竞品缺失、重复映射或与候选核心任务不匹配，候选只能停在 `REVIEW/BLOCKED`，不能进入 `SELECTED/READY_FOR_BENCH`。历史数据无法可靠拆分时保留 `insufficient_data`，不擅自补值。完整修改方案和验收条件见 [技术路线中的 1-1 竞品映射待办](docs/roadmap-technical-2026-11-11.md#待办修复选品与竞品的-1-1-对应关系)。

默认研究产量：

- Engine A 可研究任意数量，最终评选 5 个；
- Engine B 可研究任意数量，最终评选 5 个；
- Engine C 可研究任意数量，最终评选 5 个；
- 一次完整运行最终输出 15 个入选项目和 15 个完整工作台资料包。

`app-selection-loop` 的完成边界是 `READY_FOR_BENCH`：完成研究、三路线独立评选、资料包、统一网站入库和开发排期，但不直接开发这 15 个 App。开发由独立工作台或后续 `app-build-loop` 消费资料包执行；未来若需要“一口气从选品到开发”，再由更上层工厂 Loop 调度这两个 Loop，而不是把研发细节塞进选品总控。

## 飞书选品概述

选品报告或专项调查成功入库并获得可访问的网址后，可以执行一次飞书概述推送。通知使用独立技能 [`app-selection-feishu-publisher`](/Users/xmm/.codex/skills/app-selection-feishu-publisher/SKILL.md)，也可以脱离总控对某一份报告单独调用。

正式入选报告的卡片必须包括：

- 本期最终选出的全部项目名称、产品形态，并按 A / B / C 三条路线分别展示；
- 每个项目的参考品或竞品名称与对象类型；真实 App 优先链接官方 Apple App Store / Google Play，非 App 研究对象保留证据来源；
- 每个项目的生产资料包下载地址；
- 本期汇总报告网址；
- 入选数量、资料包数量和推送结果。

专项调查没有 `ROUTE_SELECTED`、但存在 `ROUTE_WATCH` 深研项目时，也允许推送调查卡片。卡片必须明确显示“深度研究数量、正式入选 0 个、WATCH”，列出可点击的参考 App 和完整调查网址，并注明授权、真实订单或结算验证通过前不进入开发台；不得伪装成已选品或已立项。

统一网站的“选品报告”列表和单份报告页都提供“推送飞书”按钮。一次点击对应一次明确的人工推送；按钮请求和总控自动推送都使用幂等键，网络回放不会重复发消息。

Webhook 只在运行环境中配置：

```text
FEISHU_SELECTION_WEBHOOK_URL=<飞书机器人 Webhook>
```

本地示例位于 `site/.env.example`，线上值由 Sites 环境变量管理。真实地址不进入 Git、网站前端、报告、资料包或卡片产物。完整格式、成功条件和失败处理见 [飞书选品报告发布规范](docs/13-飞书选品报告发布规范.md)。

单独调用技能时可以指定研究数量、合格候选数量和最终入选数量。默认每条路线最终选 5 个；目标数量不是强制配额，证据不足时必须少产出并说明缺口。

## 随时选品技能

除每周固定报告外，已经安装独立的 [`app-opportunity-scout` 选品侦察技能](/Users/xmm/.codex/skills/app-opportunity-scout/SKILL.md)。它可随时执行宽泛扫描或指定方向研究，并把合格机会送入对应路线的候选池；不会因为临时研究而绕过现实证据、路线评分和质量门槛。

两条入口的关系：

```text
即时侦察技能
  → 随时发现机会并建立独立证据包
  → SELECTED / BACKUP / WATCH / REJECTED
  → 通过硬门槛的候选进入对应路线候选池
  → 只与同一路线候选比较
  → 进入该路线最终 5 个时生成完整资料包

每周 AutoLoop
  → 固定时间完成全市场批量扫描
  → 每条路线分别输出候选、最终 5 个和备选
  → 共输出 15 个入选项目
  → 独立更新开发排期和网站
```

典型调用：

```text
使用 $app-opportunity-scout 宽泛扫描当前市场，给我 20 个机会和 5 个深度方案。
使用 $app-opportunity-scout 研究日本市场的老年人工具类 App。
使用 $app-opportunity-scout 围绕某个竞品扩展直接、相邻和替代机会。
使用 $app-opportunity-scout 挖掘轻量游戏中增长快但评论痛点明显的玩法。
使用 $app-opportunity-scout 复评上个月的某个候选。
```

- [`website-report.schema.json`](schemas/website-report.schema.json)：每次运行写入统一网站的不可覆盖报告契约。

## 经营模式

### 全覆盖

- 覆盖 Apple App Store、Google Play，并逐步接入 Amazon Appstore、Huawei AppGallery、Tencent Appstore 等其他商店。
- 覆盖主要国家、语言、品类、子品类和商业化模式。
- 同时扫描成熟常青产品、稳定增长产品、快速增长新品和新出现的细分需求。
- 不因为某个赛道竞争激烈就自动跳过；竞争本身也是需求已经被验证的证据。

### 多数量

- 长期实际发行和运营 1000+ App。
- 使用共享基础设施降低单个 App 的研究、开发、测试、订阅、广告、分析和发行成本。
- 建立标准化产品 brief、竞品包、功能模块、设计组件、数据埋点和商店素材流程。
- 允许多个候选并行研究、多个 MVP 并行开发、多个产品持续迭代。

### 现实证据驱动

没有具体的现实参考证据，不进入下一阶段。

不同引擎的参考证据不同：

- 竞品验证型：至少 3 个直接竞品，以及相邻或替代产品；
- 市场缺口型：至少 3 个替代方案、人工流程或工具拼接 workaround；
- 新需求型：至少 3 个独立领先信号，并增加真实行为或实验验证。

所有参考证据都需要：

- 名称或主题、来源链接、国家、平台和时间；
- 下载、收入、活跃、留存、搜索、讨论、流量或实验中的适用指标；
- 用户任务、当前价值、失败结果、迁移成本和付出；
- 明确说明学习什么、重构什么、为什么用户可能需要；
- 区分可学习机制和不可复制的名称、品牌、代码、内容与资产。

竞品仍然是 Engine A 最重要的现实参考；新需求不能伪造竞品，但必须使用替代行为、领先信号和实验补足证据。

### 单个方案少而精，整体产品数量要大

- 每个 App 只保留 1–3 个关键优化点，避免把所有想法塞进一个产品。
- 整体选品和产品组合不设“小而少”的限制。
- 用大量标准化选品和小步发行，持续积累产品数量和真实经营数据。

### 双语命名

- 候选产品和参考品保留官方或工作英文名，同时必须提供中文展示名；
- 所有给同事阅读的页面、报告、资料包和飞书卡片统一显示为 `English（中文）`；
- 英文名继续作为搜索、链接、竞品身份和内部稳定键，中文名只承担理解与沟通，不替换官方品牌；
- 网站报告字段使用 `title + titleZh`，参考品使用 `name + nameZh`。

### 参考品链接

- 参考对象是真实 App 时，必须保存 `store + storeUrl`，名称点击后优先进入官方 Apple App Store 或 Google Play；
- `url` 继续保存官网、文档、GitHub、技术标准或研究证据，供溯源使用；
- 没有可信独立商店页时使用 `storeUrl = null`，界面明确显示“证据来源”，不得使用第三方客户端或同名 App 冒充官方链接。

### 产品形态与对象类型

- 每个入选项目必须填写 `productForm`：`mobile_app`、`mobile_game`、`web_app`、`desktop_app` 或 `cross_platform`；
- 每个参考对象必须填写 `kind`，区分移动 App、手机游戏、Web 产品、桌面软件、开源项目、系统功能、开发平台、技术标准和研究报告；
- 网站在产品名附近显示形态标签，并在“选品总表”顶部提供产品形态筛选；
- 资料包、开发目标平台和飞书卡片沿用相同分类，不能把 Web/PC 项目默认写成 iOS/Android。

## 选品判断顺序

选品必须按以下顺序展开：

0. **机会从哪里产生**
   - 已有竞品、品类或玩法；
   - 用户任务、失败结果或人工 workaround；
   - 热点、GitHub、搜索、流量、技术、人口或政策变化；
   - 对应 Engine A、B 或 C，使用正确的证据门槛。
1. **用户是否真的在用**
   - DAU、WAU、MAU；
   - DAU/MAU Stickiness；
   - Session 数量、使用时长；
   - D1、D7、D30 留存。
2. **产品是否正在增长**
   - 最近 3、6、12、24 个月下载趋势；
   - 活跃用户趋势；
   - 收入和 Revenue per Download 趋势；
   - 增长是持续、季节性，还是短期买量造成。
3. **用户为什么使用**
   - 用户的核心任务和触发场景；
   - 正面评论中反复出现的价值；
   - 用户为何留存、推荐和付费。
4. **用户哪里不满意**
   - 最近 90 天和 12 个月的 1–3 星评论；
   - 高频 Bug、流程摩擦、价格、订阅、广告和隐私问题；
   - 用户正在使用的替代方案；
   - 多个竞品共同没有解决的问题。
5. **我们能否明显优化**
   - 是否能减少核心步骤；
   - 是否能提高准确率或可信度；
   - 是否能服务一个被忽略的细分人群；
   - 是否能形成更好的留存和付费闭环；
   - AI 是否真正参与核心任务，而不是只增加一个聊天框。

商店规则、技术实现和发行风险属于执行条件，不代替用户需求、竞品事实和市场数据决定选品。

## 候选进入下一阶段的硬门槛

每个候选必须有一份可审计的 `Opportunity Evidence Pack`，并符合：

- [`reference-evidence.schema.json`](schemas/reference-evidence.schema.json)；
- [`opportunity-candidate.schema.json`](schemas/opportunity-candidate.schema.json)；
- 所属引擎的原生参考门槛；
- 所属路线评分不低于该路线门槛（默认 75）；
- 数据完整度不低于 80%；
- 至少两类独立证据；
- 一个明确用户、核心任务、触发场景和当前替代方案；
- 1–3 个结果型改进；
- 下一次验证和停止条件。

没有数据来源、时间范围、现实参考和可验证用户任务的判断，不进入选品清单。

## 需要的数据

| 数据层 | 核心指标 | 用途 |
|---|---|---|
| 趋势信号 | 讨论、GitHub、搜索、流量、技术、人口和事件 | 提前发现变化 |
| 信号质量 | 增速、加速度、持续性、跨来源、问题/产品意图 | 淘汰短期噪声 |
| 市场规模 | 下载、收入、国家、平台、品类 | 判断市场是否足够大 |
| 增长质量 | 3/6/12/24 个月趋势 | 区分持续增长和短期爆发 |
| 真实使用 | DAU、WAU、MAU、Stickiness | 判断下载后是否真的有人使用 |
| 留存与参与 | D1/D7/D30、Session、使用时长 | 判断产品是否经久耐用 |
| 商业化 | IAP、订阅、RPD、ARPDAU | 判断用户是否愿意付费 |
| 用户需求 | 评论、评分、情绪、功能请求 | 找出价值和痛点 |
| 获客来源 | 关键词、排名、广告素材、投放渠道 | 判断增长来自产品还是买量 |
| 产品变化 | 更新时间线、版本说明、功能变化 | 解释增长或下降的原因 |

竞品数据基本都是第三方估算。选品时主要比较趋势、相对变化和多平台一致性，不迷信某个精确数字。

## 数据平台

### 领先信号与新需求

- 热点讨论：监控讨论增长、独立作者、跨平台扩散、持续性和问题/产品意图。
- GitHub / 开源：每日保存 Star 总数、Fork、Contributor、Release、Issue 和下载快照；先视为技术供给信号。
- 搜索趋势：监控 7/30/90 天、同比、相关查询、国家扩散和搜索意图。
- Web / App 流量：判断访问、安装、活跃和留存是否同步，排除纯买量和一次性事件。
- 技术、人口、政策和生活阶段：记录明确变化时间、受影响人群、行为变化和需求寿命。

### 判断用户是否真的在使用

- [Similarweb App Intelligence](https://www.similarweb.com/corp/apps/)：DAU、WAU、MAU、Stickiness、Session、使用时长和留存。
- [Sensor Tower](https://sensortower.com/)：下载、收入、活跃、留存、使用时长、评论、关键词和广告的一站式数据。
- [Apptopia](https://apptopia.com/en/apptopia-base/)：下载、收入、DAU、MAU、Session 和使用时长，适合更成熟的数据研究。

### 发现增长快或长期稳定的 App

- [AppMagic](https://appmagic.rocks/)：适合游戏、细分品类、玩法、下载和收入趋势研究。
- [Appfigures](https://appfigures.com/)：下载、收入、排名、评论、更新时间线和 API，适合建立自动化选品系统。
- [AppTweak](https://www.apptweak.com/)：免费初筛下载、收入、排行榜和发行商产品组合，强项是 ASO 与关键词。

### 广告、关键词和多商店数据

- [MobileAction](https://www.mobileaction.co/)：关键词、评论、竞品广告素材和投放渠道。
- [42matters](https://42matters.com/our-app-and-sdk-intelligence)：支持 Apple App Store、Google Play、Amazon、Tencent、Huawei 等商店的 API 和批量数据。

## 经营原则

- 先研究用户需要什么、正在用什么，再决定做什么。
- 没有真实竞品、替代方案、workaround、领先信号或实验参考，不开始产品方案。
- 没有具体数据来源、时间范围和市场维度，不下增长结论。
- 优先寻找长期活跃、稳定付费或持续增长的产品，而不是只看榜单。
- 研究现有 App 的产品机制、用户价值和不足，在此基础上优化和创新。
- 全覆盖扫描、大批量候选、分层筛选和并行开发。
- 每个具体 App 的优化点要少而精，整个产品组合要多而广。
- 一个 App 对应一个清晰人群、一个核心任务、一个可解释的差异化。
- AI 只进入能减少步骤、提高正确率或形成个性化闭环的环节。
- 基于竞品先做参考版和优化假设，再通过市场测试继续改进。
- 使用共享技术和数据平台支撑 1000+ 实际 App，并持续将上线后的真实经营数据反馈到选品系统。
